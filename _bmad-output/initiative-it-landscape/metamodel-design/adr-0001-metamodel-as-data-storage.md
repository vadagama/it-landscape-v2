# ADR-0001: Метамодель как данные (EntityType registry) и хранение на PostgreSQL + JSONB

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — ответы на OQ-1…OQ-6)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Продукт «ИТ Ландшафт» (greenfield, «Small», команда 1–3 разработчика [assumption]) обещает аналитикам расширяемую метамодель: словарь сущностей/полей/связей у каждой организации свой. Research (DI-1, DI-5): все четыре референса хранят словарь как данные — LeanIX «fully configurable» с immutable-ключами полей [D2], Ardoq «metamodel = database schema… 1:1 с воркспейсом» [D3], Essential — Classes/Slots [D4], Backstage — kinds + processors в коде (самый ригидный из четырёх) [D5]. Стек в репо не зафиксирован — PostgreSQL выбран как допущение A-1 (открытый вопрос OQ-1).

## Problem

Как представить словарь метамодели (типы, поля, типы связей) — в коде или в данных — и где физически хранить инстансы с их атрибутами, чтобы расширения не требовали релиза кода, а запросы и целостность оставались простыми для малой команды.

## Decision Drivers

- Расширяемость без изменения кода (C3, DI-1) — главное обещание продукта.
- Малая команда: простота эксплуатации и запросов важнее теоретической чистоты.
- Валидация данных против схемы должна быть принудительной (write-time), иначе спраул полей.
- Сильная консистентность метамодели и данных (NFR-3) — impact-анализ не терпит рассинхрона.
- Оценочный масштаб: ≤20k сущностей / ≤100k связей [A-2].

## Considered Options

### Option 1: Core-типы захардкожены в коде

**Description**: типы и поля — классы/enum в коде; расширение = миграция + релиз.

**Pros**:
- Максимальная типобезопасность и скорость стартовой разработки.
- Простейший валидатор.

**Cons**:
- Любое custom поле/тип = релиз — нарушает главное требование (C3).
- Противоречит практикам всех четырёх референсов (у Backstage custom kind возможен без кода ядра, у остальных — конфигурация).
- Гибрид «код для core + отдельный механизм для custom» удваивает работу валидации.

### Option 2: Метамодель-как-данные + полный EAV

**Description**: реестр в таблицах, каждый атрибут инстанса — строка в `attribute_value(entity_id, field_id, value_text/value_num/...)`.

**Pros**:
- Полная нормализация, типизированные значения, точечные индексы и FK-ограничения на значения.

**Cons**:
- Запросы превращаются в pivot-конструкции; отчётность и фильтрация усложняются на порядок.
- Много строк на сущность — объём и JOIN-нагрузка.
- Существенно больше кода доступа к данным для малой команды.

### Option 3 (chosen): Метамодель-как-данные + PostgreSQL JSONB

**Description**: реестр (entity_type, relation_type, field_def, namespace) — обычные таблицы; инстансы — `entity(oid, type_key, business_id, name, parent_oid, attributes jsonb)` и `relation(oid, type_key, source_oid, target_oid, attributes jsonb)`. Валидация attributes — на записи в приложении против реестра; GIN-индексы под фильтры; traversal — рекурсивные CTE.

**Pros**:
- Расширения без миграций и релизов; один и тот же механизм для core и custom (DI-5).
- Простые SQL-запросы и отчётность; транзакционность метамодели и данных в одной БД.
- Проверенный отраслевой компромисс; обход графа на заявленном масштабе дёшев (CTE).

**Cons**:
- Нет DB-уровня типизации полей — компенсируется write-time валидатором + property-тестами.
- Фильтры по «холодным» атрибутам требуют GIN/expression-индексов по мере роста.

## Decision

**Chosen option**: Option 3.

Реестр метамодели — данные (ADR-0003 задаёт namespace-механику); хранение инстансов — две широкие таблицы с JSONB-атрибутами; единый write-time валидатор. Графовые запросы — рекурсивные CTE, при 10-кратном росте масштаба — read-модель под impact-анализ (переоценка заложена в §17 дизайн-документа). Immunitable-инварианты (ключи, multiplicity, тип поля) — часть реестра, а не схемы БД.

### Positive Consequences

- Добавление типа/поля/связи — операция над данными, без кода и релиза.
- Один валидатор для всего; governance и импорт используют ту же точку записи.
- Отчётность и интеграции — стандартный SQL, знакомый команде.

### Negative Consequences

- Ошибка в валидаторе = повреждение данных → митигируется property-тестами инвариантов и обязательным dry-run change sets.
- JSONB-фильтры медленнее колонок → митигируется GIN-индексами и выносом hot-полей в expression indexes.

## Mitigations

- Property-тесты: любая последовательность валидных change sets сохраняет инварианты реестра.
- Golden-fixture seed registry v1.0 во всех тестовых уровнях.
- Мониторинг размера таблиц и длительности traversal (RED-метрики).
