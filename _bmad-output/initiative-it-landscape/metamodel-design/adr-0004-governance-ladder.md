# ADR-0004: Governance ladder Off / Guided / Strict per namespace, неретроактивно

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — ответы на OQ-1…OQ-6)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Research (DI-6, insight 5): рынок поляризован — LeanIX жёстко защищает ключевые связи и immutable-множественности [D2], Ardoq предлагает Org-level Constraints с режимами Off/Guided/Strict, но с документированными щелями (Surveys не ограничивают, Component Overview не флагует) и неретроактивностью [D3], Backstage живёт на конвенциях префиксов [D5], Essential — только рекомендации [D4]. Комбинированный режим «Strict для ядра + Guided для расширений» в явном виде не предлагает никто — окно дифференциации (insight 5). Паттерн one-way relaxation: ослабление необратимо, ужесточение никогда не молчаливо (Ardoq rigid→flexible).

## Problem

Как принуждать к качеству модели (валидные тройки Source→Relation→Target, схема полей), не блокируя ранние этапы внедрения, когда данных мало и словарь ещё плывёт — и при этом не создать «щели», через которые невалидные данные проникают мимо контроля.

## Decision Drivers

- Ранний этап: жёсткость отпугнёт первых пользователей; зрелый этап: отсутствие жёсткости = спраул.
- Неретроактивность: ужесточение не должно ломать существующие данные (паттерн Ardoq).
- Единственная точка записи (Catalog Service) позволяет не повторять «щели» Ardoq.
- Дифференциация: «Strict на ядро, Guided на расширения» в одном механизме.

## Considered Options

### Option 1: Без governance (конвенции, Backstage-стиль)

**Description**: валидация только синтаксическая; семантика на совести пользователей.

**Pros**:
- Нулевая стоимость реализации.

**Cons**:
- Спраул полей и связей — главный страх аналитиков и причина недоверия к EAM-инструментам.
- Импорт приносит мусор без предупреждений.

### Option 2: Всегда Strict (LeanIX-стиль immutable-жёсткости)

**Description**: любая невалидная тройка/поле отклоняется всегда и для всех.

**Pros**:
- Максимальное качество данных с первого дня.

**Cons**:
- Невозможно загрузить legacy-данные, не соответствующие ядру (а это первый сценарий миграции клиента).
- Противоречит продукту «Small» с ранними пилотами.

### Option 3 (chosen): Лестница Off / Guided / Strict на namespace

**Description**: `namespace.governance_mode ∈ {off, guided, strict}`. Валидатор проверяет тройки и схему полей при каждой записи: `guided` (default) — предупреждение + создание + пометка в отчёте; `strict` — отказ HTTP 422; `off` — без семантической проверки (синтаксическая остаётся). Ядро (`core`) — Strict по умолчанию; новые extension-namespace — Guided. Ужесточение — только через change set с dry-run-отчётом нарушений; ослабление — необратимо (one-way). Существующие данные при ужесточении помечаются в `/v1/validation/report`, не блокируются (неретроактивность).

**Pros**:
- Плавное ужесточение по мере зрелости данных; отчёт валидации — самостоятельная продуктовая ценность.
- «Strict на ядро + Guided на расширения» — дифференциатор (insight 5).
- Одна точка записи закрывает щели (у Ardoq их несколько точек входа).

**Cons**:
- Валидатор и отчёты — заметный объём работы (S4).
- Дисциплина: режимы надо не забыть поднять после пилота (риск застрять в Guided).

## Decision

**Chosen option**: Option 3.

Дополнительные фиксации: (1) синтаксическая валидация (типы полей, обязательность, формат ключей) — всегда, от режима не зависит; отступление от семантики — только тройки и имена полей по namespace-режиму; (2) отчёт валидации — вычисляемый на чтении (GET /v1/validation/report), не материализуется (избегаем рассинхрона); (3) `core` namespace может быть понижен до Guided только change set'ом с явным подтверждением — решение владельца workspace, не разработчика.

### Positive Consequences

- Ранние пилоты не блокируются, зрелые инсталляции получают контроль.
- Отчёт валидации даёт измеримую метрику качества модели (KPI для аналитиков).

### Negative Consequences

- Guided-режим допускает накопление невалидных троек → митигируется отчётом и переодическими ужесточениями.
- Two-modal поведение системы сложнее в тестировании (матрица режимов в тест-плане S4).

## Mitigations

- Тестовая матрица всех точек записи × 3 режима (E2E).
- UI-индикатор режима namespace рядом с редактором связей (предупреждение до отправки).
- Дефолт Guided для расширений и строгий дефолт для core — безопасная стартовая конфигурация.
