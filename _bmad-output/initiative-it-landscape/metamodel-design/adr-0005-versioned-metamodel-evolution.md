# ADR-0005: Версионированная эволюция метамодели — change sets + снапшот + dry-run

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — ответы на OQ-1…OQ-6)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Research (DI-7, insight 6): формальное версионирование метамодели отсутствует у всех четырёх референсов — LeanIX живёт audit log'ом и переводами вместо переименований [D2], Ardoq делает необратимые one-way конверсии [D3], Essential ближе всех: Essential Update Pack — «a script that encodes the changes to the meta model», применяемый на снапшот репозитория, с отдельной версией метамодели, независимой от версии платформы [D4]. Связка «versioned change scripts + sandbox + отдельная версия метамодели» — ready-made каркас и заявленная точка дифференциации продукта.

## Problem

Как позволять администраторам изменять метамодель (типы, поля, связи, режимы governance) так, чтобы: ошибки были обратимы, история изменений воспроизводима, изменения были переносимы между инсталляциями (паки вертикалей DI-10), а версия словаря была наблюдаема отдельно от версии продукта.

## Decision Drivers

- Доверие аналитиков: изменение словаря не должно уметь молча ломать данные.
- Воспроизводимость: одна и та же последовательность изменений → одна и та же метамодель (миграции между окружениями).
- Переносимость: расширение, собранное в одной организации, применяется в другой как артефакт (DI-10).
- C4/C5: immutable-ключи и additive-only для ядра — инварианты, которые механизм должен принуждать.
- «Small»: без полноценного event sourcing — только для метамодели, не для данных.

## Considered Options

### Option 1: Live-редактирование метамодели (Ardoq-стиль)

**Description**: админ правит типы/поля прямо в UI работающей системы.

**Pros**:
- Минимальный friction, простая реализация (инкрементальные правки).

**Cons**:
- Ошибки необратимы; история изменений фрагментарна.
- Нет переносимого артефакта — вертикали (DI-10) невозможны.
- Ровно то, против чего построен Essential EUP.

### Option 2: Audit-log + ручное восстановление (LeanIX-стиль)

**Description**: изменения метамодели пишутся напрямую, всё логируется; откат — вручную по журналу.

**Pros**:
- Дёшево; история есть.

**Cons**:
- Журнал не воспроизводит состояние (нет порядка/группировки операций); откат ручной и ненадёжный.
- Нет dry-run: последствия видны после, а не до.

### Option 3 (chosen): Change sets — декларативные версионируемые наборы операций

**Description**: единственный путь мутации метамодели — change set: упорядоченный список декларативных ops (`entity_type.add`, `field.add`, `relation_type.add`, `*.`deprecate, `enum_option.add`, `display_name.update`, `governance.set_mode`, `namespace.add`). Применение: снапшот (логический JSON-экспорт метамодели+данных) обязателен → dry-run на копии снапшота с diff-отчётом → apply в транзакции с bump `metamodel_version`. Change sets экспортируются/импортируются как YAML-артефакты (формат репозитория GitLab, ADR-0006). Seed метамодели v1.0 сам применяется как change set (догмат: механизм проверяет сам себя).

**Pros**:
- Обратимость (снапшот), воспроизводимость (артефакты), переносимость (паки вертикалей DI-10).
- Версия метамодели — отдельная наблюдаемая поверхность (Essential-паттерн).
- Дифференциация: уровень выше всех четырёх референсов (insight 6).

**Cons**:
- Friction: каждое изменение — через dry-run/apply → митигируется auto-apply single-op change set в режиме `off`.
- Нужен diff-вьюер и UI конструктора ops — заметная часть S3/S5.
- Логический JSON-снапшот на больших данных дорог → на [A-2] масштабе приемлемо; позже — физический снапшот БД.

## Decision

**Chosen option**: Option 3.

Фиксации: (1) запрещённые ops — `field.type.change`, `multiplicity.change`, `key.rename`, `entity_type.delete` для core (C4, C5); hard delete разрешён только для extension-элементов с каскадным отчётом; (2) версии метамодели — монотонный счётчик + человекочитаемый лейбл (`v1.3`), публикуется в API и «About»; (3) изменение core возможно только change set'ом версии ≥ второй — seed v1.0 не редактируется; (4) каждый change set атомарен (транзакция) и подписан автором (audit, DI-13).

### Positive Consequences

- «Схема-из-данных» становится дистрибутируемым артефактом — основа экосистемы (вертикали, обмен расширениями).
- Восстановление после плохого change set — минуты (restore снапшота).
- Ужесточение governance интегрировано в тот же механизм (governance.set_mode с dry-run отчётом нарушений).

### Negative Consequences

- Отсутствие мгновенного «quick edit» типа в UI — осознанный отказ (Option 1).
- Ведение двух уровней версий (продукт / метамодель) требует дисциплины документации.

## Mitigations

- Auto-apply single-op в режиме `off` — friction сводится к нулю на раннем этапе.
- Шаблоны типовых change sets в UI (добавить поле, добавить тип связи).
- Property-тесты: применение любой последовательности валидных change sets сохраняет инварианты C4/C5.
