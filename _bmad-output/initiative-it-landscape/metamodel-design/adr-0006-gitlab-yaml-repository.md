# ADR-0006: GitLab как репозиторий метамодели и данных (YAML+Markdown) — поэтапная интеграция

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — OKF уточнён: Open Knowledge Format; режим синка: ручной по кнопке)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Требование владельца продукта (2026-10-04): метамодель и все собранные данные должны храниться в GitLab; в перспективе **все изменения проходят через PR** (review-гейт); формат — **YAML + Markdown**; на первом этапе — отправка изменений в GitLab **вручную по кнопке** (режим уточнён, OQ-9). Приоритет реализации — веб-версия (FastAPI/React). «OKF» уточнено владельцем: **Open Knowledge Format**. Владелец предоставил ссылку на стандарт: OKF — открытая спека Google (v0.1, июнь 2026): директория Markdown-файлов с YAML frontmatter, концепт = один файл, связи через markdown-ссылки = граф. Решение по интеграции — ADR-0007: генерируемый Markdown-слой репозитория OKF-конформен, lossless YAML-слой — машинный контракт. GitLab — SaaS (gitlab.com), один репозиторий, PAT в secret store (OQ-7/OQ-8 решены, 2026-10-04).

Отраслевой контекст: Backstage строит каталог на YAML-дескрипторах в Git (`catalog-info.yaml`, kind/apiVersion) [research D5]; Git-backed YAML даёт review-культуру, историю и diff-ability «из коробки». При этом наш design (ADR-0005) уже имеет версионируемые change sets — артефактная модель совместима с MR-флоу.

## Problem

Как интегрировать GitLab, не задерживая веб-версию и не создавая двух конкурирующих источников истины: кто авторитетен (БД или Git), в каком порядке включать направления синхронизации, каким должен быть формат репозитория, чтобы diff-ы были review-дружественными, а будущий PR-flow (P2) не потребовал переписывания формата.

## Decision Drivers

- **Приоритет веб-версии** (явно указан владельцем) — интеграция не должна блокировать S1–S5.
- **Зрелое требование PR-flow**: изменения через review — цель, но не day 1.
- **YAML+Markdown**: человекочитаемость, diff-ability, независимая наблюдаемость и резервная копия.
- **Round-trip**: любое состояние БД ↔ репозиторий без потерь (иначе P2-импорт невозможен).
- **Один источник истины в каждый момент времени** — иначе дрейф и недоверие к данным.

## Considered Options

### Option 1: Git-first с первого дня (GitLab = единственный источник истины)

**Description**: приложение — редактор staged-изменений над Git-репозиторием; каждая правка = коммит/MR; БД — проекция-кэш.

**Pros**:
- PR-governance и полная история с первого дня; одна истина без этапа миграции.

**Cons**:
- Импорт-пайплайн, модель конфликтов, асинхронность записи — существенно сложнее и дольше; веб-версия (приоритет владельца) откладывается.
- Интерактивные сценарии аналитика (быстрое редактирование, impact) тяжело строятся поверх MR-цикла.

### Option 2: Только БД в v1, GitLab после PR-flow

**Description**: интеграцию целиком отложить на P2.

**Pros**:
- Минимум работы в v1.

**Cons**:
- Не выполняет явное требование владельца (P1 — отправка изменений в GitLab по кнопке).
- Теряются бесплатная ценность P1: независимый бэкап, наблюдаемость, история.
- Формат репозитория не обкатывается до P2 — риск переделки.

### Option 3 (chosen): Поэтапно — P1 экспорт по кнопке (БД = истина, Git = lossless зеркало), P2 PR-flow

**Description**:
- **P1 (в v1)**: БД — источник истины. Git Sync Service экспортирует состояние в детерминированный YAML+MD **по ручному запуску** (кнопка в UI): полная регенерация дерева (самозалечивает любой дрейф), батч-коммиты; GitLab — read-only зеркало (прямые правки в Git перезаписываются следующим экспортом, предупреждение в UI).
- **P2 (следующий этап)**: изменения через Merge Request: MR → CI-валидация (схема полей, тройки, governance через API приложения) → merge → webhook → импорт → apply. Change sets (ADR-0005) становятся MR — механики совпадают.

**Pros**:
- Веб-версия не блокируется; Git с первого дня даёт бэкап, историю, наблюдаемость.
- Формат обкатывается в P1 → P2 — эволюция, а не переписывание.
- Change sets = MR-ready артефакты (синергия с ADR-0005).

**Cons**:
- Два представления (БД/Git) — риск дрейфа при забытых ручных экспортах (митигируется pending-счётчиком и самозалечивающим полным рендером).
- В P1 Git односторонний — правки в GitLab вручную не попадают в систему (осознанное ограничение этапа).

## Decision

**Chosen option**: Option 3.

Формат репозитория (детерминированный, lossless, с первого дня):

```
it-landscape/
├── README.md                        # генерируемый обзор: версия ММ, статистика
├── metamodel/
│   ├── version.yaml                 # metamodel_version + история change sets
│   ├── namespaces.yaml
│   ├── entity-types/*.yaml          # тип + field defs
│   └── relation-types/*.yaml
├── change-sets/*.yaml               # применённые change sets как артефакты
├── entities/<type>/<BID>.yaml       # сущность + embedded relations
└── views/*.md                       # генерируемые Markdown-обзоры по типам
```

Правила: (1) файл на сущность, relations embedded в исходной сущности; (2) канонические ссылки `[type/]business_id`; (3) сортировка ключей и связей, LF, UTF-8 — стабильные diff для review; (4) Markdown — только генерируемые представления, не источник; (5) golden round-trip тест обязателен: export → импорт в чистую БД → export → деревья идентичны.

### Positive Consequences

- Требование владельца выполнено в v1 без задержки веб-версии.
- PR-flow (P2) включается поверх готового формата и синк-модуля.
- Git — независимая наблюдаемость и аварийная копия читаемого состояния (усиление NFR-4).

### Negative Consequences

- Риск дрейфа БД↔Git при забытых ручных экспортах — митигируется pending-счётчиком (виден в `/v1/sync/status`) и самозалечивающим полным рендером: каждый запуск синка перегенерирует репозиторий целиком из БД.
- Дублирование логики сериализации (БД-модель ↔ YAML) — митигируется единым рендером, используемым и для экспорта, и для импорта.

## Mitigations

- `/v1/sync/status` (последний успешный экспорт + pending-счётчик) и единая кнопка `POST /v1/sync/run` — операционная видимость.
- Golden round-trip тест в CI на каждое изменение сериализации.
- Документированное ограничение P1 (read-only зеркало) в UI и README репозитория.
- PAT GitLab — scoped project token в secret store (минимальные права).
