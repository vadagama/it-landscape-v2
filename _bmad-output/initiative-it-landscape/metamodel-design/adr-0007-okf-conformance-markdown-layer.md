# ADR-0007: OKF-конформность генерируемого Markdown-слоя GitLab-репозитория

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — владелец предоставил ссылку на стандарт)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Владелец предоставил ссылку на **Open Knowledge Format (OKF)** — открытую спецификацию Google (v0.1, опубликована 2026-06-12, Data Analytics/BigQuery team). Суть спеки: знание как директория Markdown-файлов с YAML frontmatter; **концепт = один файл** (путь файла = идентичность концепта); связи через обычные markdown-ссылки превращают директорию в **граф**; frontmatter — `type` (единственное обязательное поле), опционально `title`, `description`, `resource`, `tags`, `timestamp`; опциональные `index.md` (progressive disclosure) и `log.md` (история изменений). Принципы: minimally opinionated (спека задаёт поверхность интероперабельности, не контент-модель), независимость producer/consumer, format-not-platform (без SDK и проприетарных зависимостей). Google публикует reference-реализации: enrichment-агент (BigQuery), **статический HTML-визуализатор** (интерактивный граф из бандла в одном самодостаточном файле), сэмпл-бандлы; Google Cloud Knowledge Catalog умеет ingest OKF.

Требование владельца: «OKF для удобного формирования графа данных». Требование ADR-0006: lossless round-trip БД ↔ Git; типизированные relations с атрибутами; стабильные diff.

## Problem

Как сделать данные GitLab-репозитория удобно потребляемыми для построения графа (AI-агентами и инструментами экосистемы OKF), не ломая lossless round-trip ADR-0006, не создавая второй источник истины и не закладываясь на молодую (v0.1, июнь 2026) спецификацию жёстче, чем необходимо.

## Decision Drivers

- Явное требование владельца: OKF как стандарт для графа данных.
- Round-trip и типизированные связи (тип, атрибуты, multiplicity) критичны для P2 (PR-импорт) — markdown-ссылки v0.1 нетипизированы.
- OKF v0.1 молод — спека будет эволюционировать (заявлена backward-compatible эволюция); фиксация версии обязательна.
- Минимализм («Small»): OKF — слой чтения (view), не второй слой записи.

## Considered Options

### Option 1: OKF как основной формат репозитория (сущности = .md с frontmatter)

**Pros**: единый формат, максимальная нативность для OKF-экосистемы.

**Cons**: lossless round-trip типизированных связей с атрибутами через нетипизированные markdown-ссылки хрупок; валидация троек и multiplicity по markdown — хуже, чем по YAML; диффы и review страдают; риск для P2-импорта. Отклонено.

### Option 2 (chosen): OKF как дополнительный генерируемый слой

**Description**: `entities/*.yaml` (lossless, без изменений) + генерируемый из той же БД в том же экспорте OKF-бандл `views/`: концепт на сущность + индексы. Формат — контракт, генерация — детерминированная.

**Pros**: round-trip не затронут; граф из markdown-ссылок работает в reference-визуализаторе сразу; additive к v1.

**Cons**: файлов в репозитории ~2x при 20k сущностей; связи в OKF-графе без типов (v0.1).

### Option 3: Не интегрировать (оставить «трактовку открытого формата» из v1.3)

**Cons**: владелец дал конкретный стандарт; стоимость конформности низка (шаблон генератора). Отклонено.

## Decision

**Chosen option**: Option 2. Генерируемый Markdown-слой GitLab-репозитория OKF-конформен:

- OKF-бандл = `views/`: корневой `views/index.md` + `views/<type>/index.md` (пер-типовые таблицы переезжают в индексы) + концепт на сущность `views/<type>/<BID>.md`;
- frontmatter концепта: `type: it-landscape/<type>` (например `it-landscape/application`), `title` (имя сущности), `description`, `tags` (например lifecycle_status), `timestamp`; тело — таблица атрибутов + секция «# Relations» с markdown-ссылками на концепты целей связей;
- версия спеки OKF фиксируется в `metamodel/version.yaml`;
- golden-тест расширяется: обязательные поля frontmatter присутствуют, все внутренние ссылки бандла разрешаются;
- YAML-слой (`entities/`, `metamodel/`, `change-sets/`) не меняется — контракт round-trip ADR-0006.

## Positive Consequences

- Репозиторий потребляется без нашего API: AI-агенты, reference HTML-визуализатор (интерактивный граф — прямое исполнение требования владельца), Google Cloud Knowledge Catalog.
- Стандартный контракт вместо «собственного формата для Markdown» — интероперабельность и обмен (lingua franca).
- Полностью additive: API, БД, round-trip не меняются.

## Negative Consequences

- Файлов в репозитории при 20k сущностей ~2x (~20k YAML + ~20k .md + индексы) — длиннее экспорт, больше репозиторий; митигация: батч-коммиты уже есть (§17 дизайна), длительность экспорта мониторится (NFR-7, §18).
- Связи в OKF-графе нетипизированы (v0.1) — типизированная семантика остаётся в YAML и в тексте секции «Relations».
- Зависимость от молодой спеки (v0.1) — риск изменений; митигация: фиксация версии в `version.yaml`, генератор изолирован в одном модуле Git Sync Service, изменения спеки потребуют только правки шаблона.

## Mitigations

- Golden-тест OKF-конформности в CI рядом с round-trip тестом (§19 дизайна).
- Спека и reference-визуализатор — внешние, без vendoring; при поломке визуализатора бандл остаётся валидным Markdown.
- README бандла (views/index.md) явно указывает версию спеки и типы концептов.
