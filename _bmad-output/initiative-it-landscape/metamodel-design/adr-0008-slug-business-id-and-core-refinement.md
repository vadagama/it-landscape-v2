# ADR-0008: Человекочитаемые business_id (slug) и уточнение состава ядра метамодели

**Date**: 2026-10-04

**Status**: Accepted (Oleg, 2026-10-04 — предложения владельца)

**Deciders**: Oleg (product owner), Stuart (architect)

## Context

Владелец предложил пять уточнений к seed-метамодели (до первой реализации, greenfield):

1. **Идентификаторы вместо номеров**: `business_id` формата `CAP-0001` заменить на человекочитаемые сокращения на латинице — например `CAP-human-resources-management`.
2. **`it_component` → `technology`** — имя типа должно говорить само за себя.
3. **`tech_category` → `technology_category`** — то же.
4. **Разделить `organization`**: подразделения/команды компании — отдельный тип `department`; тип `organization` оставить именно для организаций (юрлица, внешние компании, клиенты, партнёры).
5. **`initiative`** должен покрывать не только проекты, но и дорожные карты продуктовых команд на квартал.

Дополнительно владелец подтвердил `oid` = UUIDv7 — это уже зафиксировано в §11.3 (изменений не требуется).

## Problem

Какой формат бизнес-идентификатора выбрать, чтобы ссылки в YAML, OKF-концептах, URL и диалогах читались глазами, не ломая стабильность идентификации (immutable business_id, OQ-2); и как разделить типы организационной структуры, не усложняя модель владения.

## Decision Drivers

- Читаемость: файлы `entities/application/APP-1c-zup.yaml`, ссылки `application/APP-1c-zup`, OKF-пути и URL должны быть самодокументирующимися (ценность для review в Git и для OKF, где «путь = идентичность»).
- Стабильность: `business_id` immutable (OQ-2) — идентификатор не должен зависеть от переименований.
- Семантика типов: смешение «Департамент ИТ» и «ООО Ромашка» в одном типе мешает фильтрации, отчётам и подсчётам.
- Минимализм: не плодить сущности без необходимости; механики (change sets, связи владения) должны остаться прежними.

## Considered Options (business_id)

### Option 1: Номера `PREFIX-NNNN` (status quo v1.4)

**Pros**: коротко, никогда не «протухает», генерация тривиальна.

**Cons**: нечитаемы — в диффах, ссылках и графе `CAP-0001` ничего не говорит; люди вынуждены держать соответствие в голове.

### Option 2 (chosen): Slug `PREFIX-slug`

**Description**: `business_id = PREFIX-slug`, slug — латиница строчными, `[a-z0-9-]`, ≤ 64 символа, уникален в пределах типа; задаётся при создании с валидацией и подсказкой автотранслита из `name`; после создания не меняется.

**Pros**: самодокументирующиеся ссылки, диффы и URL; путь OKF-концепта = идентичность (ADR-0007) получает смысл; не нужен отдельный «код элемента».

**Cons**: коллизии слагов → требование уникальности в пределах типа и ручной подбор при конфликте; при переименовании элемента slug остаётся старым (осознанно: идентификатор ≠ название); чуть длиннее номеров.

### Option 3: UUID в business_id

**Cons**: нечитаемы — те же минусы, что Option 1, без плюсов короткости; UUID уже есть на слое `oid`. Отклонено.

## Decision

1. **business_id = `PREFIX-slug`** (Option 2). Префиксы per тип: `APP`, `SYS`, `IF`, `CAP`, `PROC`, `TECH`, `TECHCAT`, `RES`, `PLAT`, `DATA`, `DEP`, `ORG`, `PERS`, `PRV`, `INIT`. Slug: `[a-z0-9-]`, начинается с буквы или цифры, содержит хотя бы одну букву, ≤ 64 символа; нормализация: строчные, пробелы/двоеточия/подчёркивания → дефис; уникальность `(type, business_id)`; immutable (OQ-2). `name` остаётся единственным местом переименований (DI-4). Пример: `APP-1c-zup`, `CAP-human-resources-management`, `PERS-maria-ivanova`.
2. **Типы**: `it_component` → `technology`; `tech_category` → `technology_category` (ключи seed — в seed change set «Metamodel v1.0», правило `key.rename` запрещено только для эволюции после релиза).
3. **Организационный слой**: тип `department` (подразделения/команды, иерархия через parent) + тип `organization` (юрлица/внешние, `subtype`: legal-entity/client/partner). Связи: `rel_person_member_of_department` (person → department, n:m), новая `rel_department_of_organization` (department → organization, n:1). Владение расширяется: `rel_business_owner` / `rel_it_owner` — source_types `[person, department, organization]`.
4. **Initiative**: поле `subtype` (`project` / `roadmap` / `program`); описание — «проект, программа или дорожная карта продуктовой команды на квартал»; иерархия «программа → проекты», «роадмап → элементы» — через системный parent-child (`parent_oid`), без новых типов связей.
5. **oid = UUIDv7** — подтверждено, без изменений (§11.3).

Итого ядро: **15 типов + 20 связей** (+ системная parent-child).

## Positive Consequences

- Ссылки, файлы, URL и OKF-пути читаются без справочника — быстрее review, ниже порог входа.
- Организационная семантика точна: отчёты «по департаментам» и «по юрлицам» не требуют разбора subtype.
- Initiative покрывает продуктовое планирование (квартальные роадмапы) без введения нового типа.

## Negative Consequences

- Slug не переименовывается вместе с `name` — возможно расхождение «slug старый, название новое»; митигация: slug — идентификатор, это норма (как код проекта); при острой необходимости — soft delete + новая сущность с переносом связей.
- Уникальность слага в пределах типа требует валидации при создании и обработки коллизий (подсказка суффикса); митигация: форма проверяет на лету.
- Человеческий фактор: опечатки в slug живут вечно; митигация: транслит-подсказка из `name` + предпросмотр итоговых ссылок в форме создания.
