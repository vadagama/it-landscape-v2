### 4. Backstage — Catalog page, entity page anatomy, Domain/System/Component pages, demo patterns
- The Software Catalog is browsable at `/catalog`; by default it shows entities owned by the logged-in user's team, with a switch to "All" to see all company entities — Backstage (backstage.io docs), n.d. (page reflects current release, site copyright 2026), accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: doc
- The catalog page provides basic inline search and column filtering to browse large entity sets — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: doc
- Starring components is supported for quick access to frequently visited components — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: pattern
- Entities enter the catalog three ways: manual registration of a YAML URL, automatic registration via Software Templates, and static registration via `catalog.locations` in app-config — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: doc
- An "Unprocessed Entities" feature exists for admins to find and diagnose entities that failed catalog processing — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: pattern
- Catalog index page is configurable purely via `app-config.yaml` in the new frontend system: pagination (on/off, offset mode, limit) and an export feature (CSV/JSON, dialog with per-column selection, custom exporter formats) — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Default catalog filters are kind, type, owner, lifecycle, tag, namespace, processing status; initial filter values are set declaratively (e.g., `initialFilter: domain` for kind; `initialFilter: all` for list) and default filters can be removed by config alone (`catalog-filter:catalog/tag: false`) — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Adding a *new* filter type requires code (a `CatalogFilterBlueprint` frontend module); only defaults/removal are config-only — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Custom columns, row actions, and table options are done by overriding the `page:catalog` extension with a custom page component (code, not config); the docs note the index page is deliberately kept minimal-footprint for easy customization but replica pages risk drifting from upstream — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Entity page tabs are organized into configurable groups via `app-config.yaml`: group titles, icons (`showNavItemIcons`), per-group content ordering (`title` alphabetical vs `natural` registration order), and group aliases for renaming/merging without reconfiguring extensions — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Which entity-content extension (tab/card) appears on which entity is expressed as a declarative "entity predicate query": a JSON/YAML filter language over entity fields (`kind`, `spec.type`, operators `$all/$any/$not`, value operators `$exists/$in/$contains`) configurable without code — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Individual entity content extensions can be re-grouped, given icons, or detached from any group (`group: false`) per installation via config — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- The entity context menu is extensible only in code (`EntityContextMenuItemBlueprint`) — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern

### 5. Common UX patterns across the four tools
- Verified this run, Backstage only: browse-default = filtered table (ownership filter first, "All" opt-in), inline search over the table, column filtering, star/bookmark for quick access, plus an admin-only diagnostic view for failed entities — synthesis of the two Backstage pages cited above, accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/ — confidence high — class: pattern
- Unverified belief (not evidenced this run; to test in round 2): the other three tools share the same skeleton — saved filter+column presets (LeanIX "saved views", Ardoq views), configurable columns, relation-click drilldown from detail pages, and dashboards/present modes aimed at demonstrating to teams. Stated as hypothesis only.

### 6. Admin-configurable (declarative) vs hardcoded catalog UI patterns
- Evidenced for Backstage (new frontend system), two clear layers: declarative/config layer in `app-config.yaml` — pagination, catalog export toggle and formats, filter defaults, filter removal, entity-page tab groups/titles/icons/order/aliases, and entity-predicate-driven content placement; code layer — new filter types, custom columns/table composition, context menu items — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- The declarative layer's content-placement mechanism (entity predicate queries over `kind`/`spec.type`/fields) is the closest documented analog to "schema-as-data screen configuration" found this run — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/catalog-customization — confidence high — class: pattern
- Whether LeanIX/Ardoq/Essential expose equivalent declarative configuration is not evidenced this run; their admin-configurability remains an open question for round 2.
