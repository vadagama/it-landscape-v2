**arc42 — the authoritative architecture-document template (closest formal analog to "HLD document")**

- arc42 is a template for architecture documentation organized into exactly 12 named sections: 01 Introduction and Goals (requirements, stakeholders, top quality goals); 02 Constraints (technical/organizational constraints, conventions); 03 Context and Scope (business/technical context, external interfaces); 04 Solution Strategy (fundamental solution decisions and ideas); 05 Building Block View (abstractions of source code, black-/whiteboxes); 06 Runtime View (runtime scenarios: how building blocks interact); 07 Deployment View (hardware, technical infrastructure, deployment); 08 Crosscutting Concepts (recurring solution approaches and patterns); 09 Architecture Decisions (important, expensive, risky or contentious decisions); 10 Quality Requirements (overview + detailed quality scenarios); 11 Risks and Technical Debt; 12 Glossary — arc42 (docs site), n.d. (© 2003–2026), accessed 2026-10-04 — https://docs.arc42.org/home/ — high — class: doc
- The reference site is positioned as "The working reference for the arc42 architecture template" with 144 practical tips and 35 worked examples; guidance depth is selected per usage mode via keywords: "lean" (streamline, agile), "thorough" (large/critical/audited systems), "essential" (what you should always document) — arc42, n.d., accessed 2026-10-04 — https://docs.arc42.org/home/ — high — class: doc
- arc42 Section 03 "Context and Scope" (verbatim core): "System scope and context … delimits your system (i.e. your scope) from all its communication partners (neighboring systems and users …). It thereby specifies the external interfaces." Business context (3.1) = "Specification of *all* communication partners (users, IT-systems, …) with explanations of domain specific inputs and outputs or interfaces", form: black-box diagram or a table titled with the system name with three columns — communication partner / inputs / outputs. Technical context (3.2) = technical interfaces (channels, transmission media) plus a mapping of domain I/O to channels — arc42, n.d., accessed 2026-10-04 — https://docs.arc42.org/section-3/ — high — class: doc
- System-linking is intrinsic to arc42: the document is scoped to one system ("your system") and enumerates its neighboring systems and external interfaces; practical tips advise: Tip 3-1 "Explicitly demarcate your system from its environment!", Tip 3-7 "If many external systems are involved, aggregate (cluster) them by explicit criteria!", Tip 3-8 "Aggregate (cluster) similar neighbour systems with ports!", Tip 3-9 "Show all (all!) external interfaces!" (#essential) — arc42, n.d., accessed 2026-10-04 — https://docs.arc42.org/section-3/ — high — class: pattern
- Section 09 "Architecture Decisions" is a first-class arc42 section ("Important, expensive, risky or contentious decisions") — i.e., per the template, ADRs live inside the system's architecture document rather than as detached artifacts — arc42, n.d., accessed 2026-10-04 — https://docs.arc42.org/home/ — high — class: doc (converges with r1/r2 Backstage-ADR findings)
- License: CC BY-SA 4.0; "Created by Peter Hruschka & Gernot Starke" (© 2003–2026), supported by INNOQ / Kröner & Starke; docs site is open source on GitHub — arc42, n.d., accessed 2026-10-04 — https://arc42.org/ (footer, retrieved via 404 page) + https://docs.arc42.org/home/ — high — class: doc

**C4 model — diagram-level analog**

- C4 model = "an easy to learn, developer friendly approach to software architecture diagramming": a set of hierarchical abstractions — software systems, containers, components, and code; a set of hierarchical diagrams — system context, containers, components, and code; supporting diagrams — system landscape, dynamic, and deployment; notation independent; tooling independent; official website written by creator Simon Brown — c4model.com, n.d., accessed 2026-10-04 — https://c4model.com/ — high — class: doc
- C4's own scoping guidance: "you don't need to use all 4 levels of diagram; only those that add value - the system context and container diagrams are sufficient for most software development teams" — c4model.com, n.d., accessed 2026-10-04 — https://c4model.com/diagrams — high — class: practice
- License: "This website and example diagrams are licensed under a Creative Commons Attribution 4.0 International License." (CC BY 4.0) — c4model.com, n.d., accessed 2026-10-04 — https://c4model.com/ — high — class: doc

**Structurizr — tooling that links a model to derived diagrams**

- Structurizr is a "models as code" tool designed for the C4 model: "you write Structurizr DSL to create multiple software architecture diagrams from a single model"; "created by the author of the C4 model and remains the reference implementation"; shipped DSL example defines person/softwareSystem/containers + relationships once, then derives systemContext and container views from it ("creates two diagrams based upon a single set of elements and relationships") — structurizr.com, n.d., accessed 2026-10-04 — https://structurizr.com/ — high — class: pattern
- Tooling surface: browser playground; "local" viewer; self-hosted server (open core + pre-built binaries with "features designed for use in enterprise environments (license required)"); export CLI to PlantUML, Mermaid, or static HTML; free open-source MCP server to "parse & validate DSL, export diagrams to PlantUML & Mermaid, and manage workspaces" — structurizr.com, n.d., accessed 2026-10-04 — https://structurizr.com/ — high — class: doc
