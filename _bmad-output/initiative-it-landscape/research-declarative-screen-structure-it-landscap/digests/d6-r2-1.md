### Q5 — PostgreSQL FTS for JSONB (PG 18 current docs; project targets PG 16 — features below exist in 16 unless noted)

- `jsonb_to_tsvector([config regconfig,] document jsonb, filter jsonb) → tsvector` documented: selects items requested by `filter` (jsonb array of keywords "string", "numeric", "boolean", "key", "all"), converts each to a tsvector with the same normalization as to_tsvector, concatenates in document order; position info generated as if one stopword separates selected items; caveat: "document order" of jsonb object fields is implementation-dependent — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/functions-textsearch.html — high — class: pattern
- `to_tsvector` also has json/jsonb overloads (indexes every string value of the document, no filter); `ts_headline` likewise has json/jsonb overloads returning highlighted JSON — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/functions-textsearch.html — high — class: pattern
- Stored generated column + GIN fully documented: `ALTER TABLE … ADD COLUMN textsearchable_index_col tsvector GENERATED ALWAYS AS (to_tsvector('english', coalesce(title,'') || ' ' || coalesce(body,''))) STORED` + `CREATE INDEX … USING GIN (textsearchable_index_col)`; advantages vs expression index: queries need not repeat the config and are faster (no per-query to_tsvector recomputation); expression index is simpler and uses less disk — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/textsearch-tables.html — high — class: pattern
- Expression-index constraint: only the two-argument (explicit-config) `to_tsvector` may be used in an expression index, because index contents must be independent of `default_text_search_config`; queries must use the same config to hit the index — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/textsearch-tables.html — high — class: pattern
- `websearch_to_tsquery` safe for raw user input: "will never raise syntax errors"; syntax: quoted text → phrase, `or` → OR, `-` → NOT, other punctuation ignored; cannot express weights or prefix matching — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/textsearch-controls.html — high — class: pattern
- Weighted ranking recipe re-confirmed: `setweight(to_tsvector(config, coalesce(field,'')), 'A'..'D') || …` then `ts_rank_cd` with weights {D,C,B,A} = {0.1, 0.2, 0.4, 1.0} and normalization bitmask (32 = rank/(rank+1) cosmetic scaling); docs warn ranking "can be expensive… I/O bound" — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/textsearch-controls.html — high — class: pattern
- `ts_headline` XSS warning re-confirmed verbatim category: output "not guaranteed to be safe for direct inclusion in web pages… does not provide an effective defense against… XSS"; additionally "uses the original document, not a tsvector summary, so it can be slow and should be used with care" — PostgreSQL (current docs), n.d., accessed 2026-10-04 — https://www.postgresql.org/docs/current/textsearch-controls.html — high — class: failure

### Q6 — Synthesis: faceted search for ≤20k entities (FastAPI + PostgreSQL 16, JSONB attributes)

Evidence-grounded synthesis; items marked [inference] are design reasoning built on the cited evidence, not vendor claims:

- Scale signal: Backstage's first-party PG engine is explicitly positioned for "ten thousands of indexed documents" without any auxiliary service — Backstage, n.d., accessed 2026-10-04 — https://backstage.io/docs/features/search/search-engines/ — medium — class: practice. At ≤20k entities this range directly covers the project's scale.
- [inference] Server-side responsibilities (all natively documented in PG 16): keyword search via generated tsvector column + GIN over `jsonb_to_tsvector('…', attributes)` and setweight-combined name/description; user-input parsing via `websearch_to_tsquery` (never errors on raw input); ranking via `ts_rank_cd`; pagination; declarative filter→SQL translation (Ardoq 44086 pattern: field→operator rules, ALL/ANY, enum multi-select, missing-value → `attributes ? 'key'` / `->>'key' IS NULL`); facet counts via GROUP BY over the same JSONB expressions.
- [inference] Client-side responsibilities (per Backstage concepts + getting-started): result presentation and per-result custom components (predicate on `result.type`), filter UI state, in-page filtering only of already-fetched result sets; highlights must be sanitized client-side because `ts_headline` output is not XSS-safe (PG docs warning), and Backstage makes ts_headline-based highlighting optional/disable-able for performance.
- [inference] No external engine justified at this scale on the evidence: the PG engine exists precisely to "avoid maintaining another external service like Elasticsearch"; Backstage schedules complete bulk rebuilds (documented non-goal: incremental indexing), which at ≤20k entities is trivially cheap; justified only when needing ES-specific capabilities visible in the differential docs — fuzziness/prefix tuning, batch tuning at scale, token-rotating auth (Backstage search-engines page) — none of which the project requirements state.
- [inference] Saved filters: store the filter definition (declarative rule JSON) server-side; optional history via periodic snapshots follows Ardoq's saved-query nightly-snapshot pattern (r1 evidence) — cheap to replicate with a PG table.
- [inference] Indexing strategy: unlike Backstage (external index rebuilt on schedule), a PG-native design can index synchronously via generated columns (always current, no scheduler); a separate search document table is only needed if attributes live across joined tables.
