### Ardoq — Perspectives & Saved Perspectives (Q2)
- Perspectives let end users (not just admins) filter, group, or conditionally format data in a view; examples: group all Applications by the reference "Owned by"; heatmap of capabilities using field "Market Differentiation" — grouping/formatting binds to metamodel fields and reference fields. — Ardoq Help Center, article 44114, written 2023-08-28, accessed 2026-10-04 — https://help.ardoq.com/en/articles/44114-perspectives — high — class: doc
- Perspective management is a "Manage" window with three config areas — Filters, Grouping, Formatting — applied with Apply / Apply & Close; multiple filters/groupings/formattings can combine in one view. — Ardoq Help Center, 44114, 2023-08-28, accessed 2026-10-04 — https://help.ardoq.com/en/articles/44114-perspectives — high — class: practice
- Quick Filters live at the bottom of the Navigator and list the Components and References present in the current view (e.g., check reference "Runs on" to narrow scope); users can also right-click a component/reference in-view to filter. — Ardoq Help Center, 44114, 2023-08-28, accessed 2026-10-04 — https://help.ardoq.com/en/articles/44114-perspectives — high — class: practice
- Saved Perspectives: a configured perspective can be named and saved; saved ones appear under the Perspective icon; deletion via Manage Perspectives → Saved Perspectives. — Ardoq Help Center, 44111, updated 2025-08-19, accessed 2026-10-04 — https://help.ardoq.com/en/articles/44111-saved-perspectives — high — class: practice
- A default perspective for all users in a workspace exists: save a perspective, then apply it as default via workspace properties (FAQ answer, admin-level operation). — Ardoq Help Center, 44111, updated 2025-08-19, accessed 2026-10-04 — https://help.ardoq.com/en/articles/44111-saved-perspectives — high — class: practice

### Ardoq — Field Groups (beta) & Component Overview page (Q2)
- Baseline behavior: on the Component Overview page a component's fields render as a single flat, alphabetical list when no groups are configured — i.e., default field layout is generated, not hand-designed. — Ardoq Help Center, 757885 "[Beta] Field Groups", written 2026-08-25, accessed 2026-10-04 — https://help.ardoq.com/en/articles/757885-field-groups-beta — high — class: doc
- Field Groups (beta, written 2026-08-25): an administrator bundles related fields into labeled sections on the Component Overview page (example: "Cost" group bundling Total Cost, CAPEX, OPEX, Total Direct Cost); configured under **My Organization > Fields/Metamodel Constraints** — field-group configuration lives in the same admin area as metamodel constraints. — Ardoq Help Center, 757885, 2026-08-25, accessed 2026-10-04 — https://help.ardoq.com/en/articles/757885-field-groups-beta — high — class: pattern
- Field Groups are centrally managed and type-scoped: "any component of that type shows the group's fields together as a labeled section"; every user sees the same organized layout, no per-user setup. — Ardoq Help Center, 757885, 2026-08-25, accessed 2026-10-04 — https://help.ardoq.com/en/articles/757885-field-groups-beta — high — class: practice
- Field Groups are opt-in beta enabled only by Ardoq CSM/Support; absent groups → page unchanged. Rollout is flag-gated per organization. — Ardoq Help Center, 757885, 2026-08-25, accessed 2026-10-04 — https://help.ardoq.com/en/articles/757885-field-groups-beta — high — class: doc
- New Component Overview page is a fixed 5-tab shell — Overview (read-only summary), Fields (edit), References (relationships), Viewpoints (visualizations), Styles (appearance in diagrams) — with standalone-page and drawer modes. — Ardoq Help Center, 523928, "updated this week" (≈2026-10), accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- Priority Fields are admin-configured **per component type** via Organization Settings → Priority settings (checkbox table of all fields for the type); they then appear first on Fields and Overview tabs for all users; if none configured the section is hidden. — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- Field order on the Component Overview page follows the order set in the workspace manager (the metamodel); Fields tab sort offers "Default order (set by an admin in the metamodel)" vs Alphabetical. — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- The References tab is metamodel-driven: references are grouped by **triple** (source component type → reference type → target type); when metamodel constraints are configured, **all permitted triples appear — including those with zero existing instances** ("This is by design, so you can create new references of any allowed type"); a missing reference type means an admin has not configured it for that component type. — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- Editors are chosen by field type, not per-screen config: "Each field type has a specialized editor — text boxes, dropdowns, date pickers, rich text editors"; system fields (Ardoq ID, Created By, Created Date) are read-only at the bottom; calculated fields are always read-only because they are "automatically generated by a Gremlin query". — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- The Overview tab's visual preview shows the admin-configured **priority viewpoints** for the component type (dropdown when 2+, "Ardoq default" chip, fallback to Ardoq's per-type Default overview) — the type↔viewpoint binding is admin config. — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- Styles are per-component data (icon from 250+ incl. ArchiMate/BPMN/EDGY sets, custom image, shape, color/hex), affecting appearance "in all block diagrams, dependency maps, and other visualizations" — styling config is stored on the entity, the visualization engines are fixed product code. — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: pattern
- Documented current limitations of the declarative-ish layout features: no audit log tab yet, no inline editing on Overview tab, unfiltered long permitted-triple lists, slower loads with hundreds of references, empty Priority Fields section when enabled but unconfigured — several flagged "planned". — Ardoq Help Center, 523928, ≈2026-10, accessed 2026-10-04 — https://help.ardoq.com/en/articles/523928-new-component-overview-page — high — class: failure

### Backstage — New Frontend System blueprints (Q3)
- A frontend plugin is `createFrontendPlugin({ pluginId, extensions, routes })` from `@backstage/frontend-plugin-api`; extensions are created via **blueprints** (e.g., `PageBlueprint.make({ params: { routeRef, path, title, icon, loader } })`); the page's `title` and `icon` automatically populate the app sidebar; page components are always lazy-loaded via React.lazy. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/frontend-system/building-plugins/index — high — class: pattern
- `EntityContentBlueprint` (from `@backstage/plugin-catalog-react/alpha`) is the declarative way a plugin contributes content to the entity page: `{ path, title, loader }`, rendered at a route with in-line navigation between content — evidence that entity-page tabs/sections are extension points, not hardcoded UI. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/frontend-system/building-plugins/index — high — class: pattern
- Plugins are installed into an app via default export without code references ("how users of our plugin are able to seamlessly install the plugin package in a Backstage app without having to reference the plugin instance through code"); Utility APIs are declared via `ApiBlueprint` and integrators may replace implementations. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/frontend-system/building-plugins/index — high — class: pattern
- Freshly generated plugins are "still templated for use in the legacy frontend system, and you will need to replace the existing plugin wiring code" — NFS is the target but the default scaffolding lags (as of this docs snapshot). — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/frontend-system/building-plugins/index — high — class: doc

### Backstage — app-config schema & visibility (Q3)
- Configuration is a schema stitched from all packages' contributions (each package exposes one via a `configSchema` field in package.json, inline JSON schema or `.d.ts`/`.json` file); meta-schema is a **superset of JSON Schema Draft-07** with custom `visibility`/`deepVisibility` keywords; values: `frontend` (visible in frontend+backend), `backend` (default, backend only), `secret` (backend only, excluded from logs; frontend+secret conflict is a schema-merge error). — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/conf/defining/ — high — class: pattern
- Official guidance pushes back on config sprawl: "Make limited use of static configuration… options that you want to be able to change for different deployment environments should be static configuration, while it should otherwise be avoided"; prefer objects over arrays; avoid new top-level keys. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/conf/defining/ — high — class: practice
- Validation tooling: `backstage-cli config:check`, frontend view via `config:print --frontend`. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/conf/defining/ — high — class: practice

### Backstage — custom kind cost (Q4)
- The catalog backend is kind-agnostic ("from a storage and API standpoint, does not care about the kind"); adding a new kind = permit it through validation (custom `CatalogProcessor` validating against your JSONSchema via `entityKindSchemaValidator`, registered through `catalogProcessingExtensionPoint` in a backend module) + make plugins understand it. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/extending-the-model/ — high — class: pattern
- Frontend cost is the dominant one: "Adding a kind has a very large impact… There will be many places where code checks `if (kind === 'X')` for some hard coded `X`, and casts it to a concrete type" from `@backstage/catalog-model`; a custom kind needs an own namespaced `apiVersion` (e.g., `my-company.net/v1`), a TypeScript type + JSONSchema in an isomorphic package, and a processor. No declarative (config-only) kind registration exists in this doc. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/extending-the-model/ — high — class: pattern
- Adding a new **type** within an existing kind: "relatively little effort and carries little risk" — backend accepts any type value, but plugins "may have to be updated" for behaviors attached to the type; specific types make contextual plugins easier. — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/extending-the-model/ — high — class: practice
- Changing core validation rules (envelope/metadata, `BuiltinKindsEntityProcessor`) is "high risk… not recommended"; metadata/spec unknown fields are stored verbatim but extending them is cautioned against (collision with future core). — Backstage docs, accessed 2026-10-04 — https://backstage.io/docs/features/software-catalog/extending-the-model/ — high — class: practice

### RJSF / JSON Forms (Q5)
- RJSF docs banner shows current version **v6.11.0**. — RJSF docs (rjsf-team.github.io), accessed 2026-10-04 — https://rjsf-team.github.io/react-jsonschema-form/docs/quickstart — high — class: version
- RJSF split confirmed: `<Form schema={} validator={} />` renders entirely from JSON Schema; presentation customization is a **separate `uiSchema` prop** keyed by property path (e.g., `{'ui:classNames': …}`, per-property objects); a validator implementation is required since v5 (recommended `@rjsf/validator-ajv8`); `formData` prefills; handlers `onChange/onError/onSubmit/onFocus/onBlur`; uncontrolled by default. — RJSF docs, accessed 2026-10-04 — https://rjsf-team.github.io/react-jsonschema-form/docs/quickstart — high — class: pattern

### Boundary synthesis (Q6 — from the above evidence only)
- **Config/data-driven in Ardoq:** component detail field layout (fields, order from workspace manager, Priority Fields per type, Field Groups per type), the set of editable references (metamodel triples/constraints, including zero-instance permitted triples), per-type priority viewpoints shown on Overview, perspective filter/group/conditional-format definitions and workspace-default perspective. — synthesis from Ardoq Help Center articles 44114/44111/757885/523928, accessed 2026-10-04 — high — class: pattern
- **Fixed code in Ardoq:** the 5-tab Component Overview shell, the visualization product set (block diagrams, dependency maps, etc. — styles/perspectives only re-skin/re-filter them), field-type-specific editors, calculated-field (Gremlin) machinery. — synthesis, Ardoq Help Center, accessed 2026-10-04 — high — class: pattern
- **Config in Backstage:** app-config.yaml (schema-validated, visibility-filtered frontend subset), extension presence/parameters via config, plugin install via features; **code (TypeScript blueprints)**: pages (`PageBlueprint`), entity content/tabs (`EntityContentBlueprint`), Utility APIs — UI structure is contributed as code-packaged extensions, then only toggled/parameterized by config; and the official docs explicitly discourage broadening static config beyond per-environment options. — synthesis from backstage.io docs, accessed 2026-10-04 — high — class: pattern
- **Kind vs type asymmetry (Backstage):** schema-as-data stops at the entity model edge — new kind = processor code + schema package + plugin updates ("very large impact"), while new type = data value with small risk. Metamodel-as-data products (Ardoq) push this boundary further out: component types and their fields are admin-editable data. — synthesis, accessed 2026-10-04 — high — class: pattern
- **Forms:** RJSF formalizes the split the EA tools approximate: data schema (drives fields/validation) vs uiSchema (drives presentation) vs code (custom widgets/templates). — synthesis from RJSF quickstart, accessed 2026-10-04 — high — class: pattern
