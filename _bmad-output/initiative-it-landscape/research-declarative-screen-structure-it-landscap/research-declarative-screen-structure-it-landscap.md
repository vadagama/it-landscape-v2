# Technical research: Declarative modular screen structure for IT Landscape — EA catalog UI (LeanIX, Ardoq, Essential, Backstage)

**Decision this research serves:** Спроектировать оптимальную декларативную и модульную структуру экранов для продукта «ИТ Ландшафт» — просмотр всех сущностей EA, демонстрация командам с дрилдауном, демонстрация связей, дорожные карты развития продуктов, тех-радар, ADR/HLD/RFC, поиск по любым атрибутам и описаниям, графы связей.

## Executive summary

**Ответ на решение:** оптимальная структура экранов «ИТ Ландшафта» — не копия одного инструмента, а конвергенция четырёх референсов вокруг одного правила: **всё, что есть в метамодели (типы, поля, связи, секции, порядок) — данные; все виды отображения (таблица, граф, timeline, радар) — фиксированные модули, параметризуемые этими данными.** Это правило выводится независимо из Ardoq (метамодель-driven layout вплоть до порядка полей и zero-instance троек), Backstage (цена нарушения: новый kind = «very large impact» из-за проверок `if (kind === 'X')` в коде) и LeanIX (контрпример: отчёты, хардкодно привязанные к стандартной метамодели, и метамодель как vendor Add-On с 4-недельным SLA).

**Три находки, определяющие дизайн:**

1. **Карточка сущности = табнутый профиль, рендеримый из метамодели; связи = first-class примитив на всех экранах.** Тройка Source→Type→Target появляется везде: в карточке (Ardoq References-таб), в инвентаре (references-as-columns), в графе (drilldown = re-root, не модалка), в радаре (join с приложениями). Для 20 типов связей v1.5 это один переиспользуемый компонент отображения связей вместо реализации на каждый экран.
2. **Поиск и фильтрация решаются PostgreSQL без внешнего движка при целевом масштабе ≤20k сущностей.** Полный рецепт документирован и верифицирован: stored generated tsvector + GIN поверх `jsonb_to_tsvector`, парсинг ввода `websearch_to_tsquery` (никогда не падает на сыром вводе), ранжирование `ts_rank_cd`; первый-party PG-движок Backstage заявлен «performs well with ten thousands of indexed documents». Уровни UI: ⌘K omnibox (ID-first по business_id, permission-aware) + декларативный advanced builder (field→operator, ALL/ANY).
3. **Радар, дорожная карта и демонстрация — линзы над инвентарём, а не отдельные миры.** Радар «связанный с продуктами» — это report поверх связей (паттерн LeanIX; ни TW, ни Backstage, ни AOE такого не умеют); дорожная карта — проекция date-range/date полей (бары/ромбы) над связями initiative→сущность; демонстрация командам — сериализуемые состояния и demo-shell над живыми view (Ardoq presentations/explore-mode).

**Caveat:** доказательства по LeanIX — снапшоты 2020–2021 (продукт под SAP эволюционировал, живая документация — JS-SPA); Open questions фиксируют, что перепроверить перед финализацией дизайна (русский FTS-конфиг на живом PG16, текущие экраны LeanIX, лимиты граф-рендеров).

## D1. Каталог и навигация: инвентарь, карточки сущностей, drilldown

**LeanIX (архивные primary-docs, 2021; live-докуметация недоступна — 301 на JS-SPA SAP Help Portal [7]).** Инвентарь — центральный экран: все объекты хранятся как Fact Sheets; по умолчанию показываются только Active, архив — под фильтром-корзиной и не считается в квоту издания [1]. Табличный вид: переключатель «As Table», по умолчанию имя+тип, «Select columns» со всеми полями выбранного типа, eye-иконки по категориям, drag-to-reorder колонок, экспорт таблицы в Excel [1]. Smart search ищет по именам, тегам, категориям **и связям**; настройки фильтров сохраняются и сбрасываются; «Dual Axis Filtering» сужает поиск фильтрами над списком [1]. Правый сайдбар инвентаря: New Fact Sheet, Recently Viewed, Delete с обязательной причиной, Clone (атрибуты+связи+документы, но не комментарии/опросы/метрики), Import [1]. Карточка Fact Sheet = **Header / Body / Sidebar**: header — имя, тип, теги, качество данных, subscribe, comments, documents, metrics, surveys, change history + edit/print/delete/clone; body — контент, «structured in sections» по шаблону типа (у Project FS — секции «Project Environment», «Project Setup»); sidebar — интеграции, To-Dos, recently viewed, related diagrams [2] (верифицировано: вторая архивная страница подтверждает секционную структуру с per-section editing и header-hosted модулями; тот же publisher — ограничение отмечено). Отчёты несут «View dropdown»: view строится на полях типа, **полях связей** (Total annual cost живёт на связи Application–IT Component), полях связанных FS или тегах; 14 стандартных view (Lifecycle, Functional/Technical Fit, Business Criticality, Aggregated Obsolescence Risk, …) + «individualized views» из собственных атрибутов и tag groups [3]. Дашборд (KPI-типа: Data Quality из required fields, распределение redundancy, Gartner TIME) существовал уже в 2021, но был помечен deprecated [4]. Маркетинговый регистр (medium): customizable dashboards с историческими трендами, configurable surveys/to-dos/quality seals для стейкхолдеров вне ИТ [5]; transformations overview с filter&focus, inline editing и bulk actions [6].

**Ardoq (primary docs, свежие 2026).** Homepage новой версии = admin-configured карточки Quick Actions (карточка привязана к типу компонента или воркспейсу, ссылки на dashboards/reports/presentations/surveys/viewpoints) + Key insights (виджеты метрик вроде ownership gaps с drilldown в отчёт) + pinned dashboard целиком; конфигурация org-wide в Organization Settings → Home Settings, доступ через ⌘K-палитру; per-user кастомизации нет; собственный best practice Ardoq — homepage «launch pad, not destination» [8]. Фильтры дашборда создаются на нём же, рендерятся наверху при любом встраивании, AND-логика, выбор зрителя временный (сброс по refresh) [8]. **Component Overview = табнутый профиль из 5 табов**: Overview (read-only: имя/тип/описание, Priority Fields, summary связей, visual preview), Fields (inline editing, Priority Fields сверху, системные поля снизу, calculated — read-only), References (группировка **тройками Source→Type→Target**; клик по группе → панель с полями связи и полями связанного компонента; multi-target создание; inline-создание отсутствующего target), Viewpoints (все viewpoints с этим компонентом, hover-preview), Styles (250+ иконок, включая наборы ArchiMate/BPMN/EDGY) [9]. Три точки входа (глобальный поиск hover→Open; Data Inventory click; из визуализации) × два режима рендера: standalone (с деревом Components Browser) и drawer («в контексте», без дерева) [9]. Components Browser: дерево всех компонентов воркспейса, поиск, drag-and-drop re-parent; parent-child **намеренно выведен** из References-таба [9]. Priority Fields — admin-настройка per тип (Organization Settings → Priority settings) [9]. Известные ограничения карточки: нет audit-log таба (в планах), Overview не inline-editable (в планах), при metamodel constraints перечисляются все permitted triples включая zero-instance («длинный список»), медленная загрузка на сотнях references [9]. В roadmap: замена списка связей на визуальную окрестность «one step out» + переход по клику на связанный компонент [9].

**Essential.** Essential Viewer представляет репозиторий как **порталы → panels → sections → reports/catalogues** (стартовые порталы: Enterprise Architecture, View Library; админ добавляет свои); History-таб возвращает к посещённым отчётам сессии; hover по настраиваемому логотипу — quick-access бар ко всем порталам [11][12]. Порталы и их содержимое конфигурируются в инструменте репозитория, не в viewer UI [12]. Sitemap подтверждает отдельные страницы: Application Catalogue, Application/IT Asset/Business Capability/Decision/Roadmap Dashboard, Enterprise Architecture Navigator, Viewer and Portal Set-up, Customise Essential Viewer, Adding/Creating New Reports, Dynamic Query Tool v2 (сохранение как Query / Catalogue), Export to PowerPoint [13].

**Backstage.** Каталог: по умолчанию показывает сущности команд пользователя, переключатель «All» [14]; inline search, column filtering, starring; admin-only диагностический экран Unprocessed Entities [14]. Два маршрута: `CatalogIndexPage` (/catalog) и `CatalogEntityPage` (/catalog/:namespace/:kind/:name) с per-kind кастомизацией через `entityPage` switch [16]. Org-плагин: Group Page, User Profile, opt-in карточки (ownership, members-list), сайдбар-элемент MyGroupsSidebarItem (скрыт без членства, подменю при нескольких группах) [17]. New Frontend System: pagination, экспорт (CSV/JSON с выбором колонок), дефолты и удаление фильтров — **только app-config**; новые типы фильтров, кастомные колонки, пункты контекстного меню — **код** (Blueprints); таб-группы карточки сущности (заголовки, иконки, порядок, алиасы) — конфиг; размещение карточек/табов по сущностям — **декларативные entity predicate queries** (`$all/$any/$not`, `$exists/$in/$contains` по kind/spec.type/полям) [15].

**Синтез D1 — паттерны для структуры экранов:**

1. Карточка сущности во всех трёх читаемых инструментах = «табнутый профиль + типизированные связи отдельной зоной» (Ardoq: 5 табов [9]; LeanIX: Header/Body/Sidebar с секциями [2]; Backstage: per-kind страница с таб-группами [15]).
2. Связи группируются тройкой Source→Type→Target с click-through на обе стороны — прямой паттерн для модели из 20 типов связей [9][15].
3. Иерархия (parent-child) — отдельное дерево/браузер, не элемент списка связей [9].
4. Двухслойная декларативность: admin-конфиг (layout секций, Priority Fields, колонки таблицы, дефолты фильтров, home-карточки) vs код (новые типы фильтров, кастомные колонки, визуализации) [8][9][15].
5. Сохранённые фильтры/views — first-class объекты: LeanIX savable filters + 14 стандартных view [1][3]; Ardoq фильтры дашбордов и Perspectives [8][10]; Essential save-as-Query/save-as-Catalogue [13].
6. Дашборд для демонстрации командам — отдельный top-level объект (Ardoq dashboards [8], Essential dashboards-in-portals [12][13], LeanIX dashboards [4][5]).
7. Drilldown двух режимов — drawer «в контексте» vs standalone — выбор по точке входа [9].

## D2. Графы связей и impact-анализ

**Backstage (source-verified: файлы monorepo master, accessed 2026-10-04).** Плагин `catalog-graph` поставляет три поверхности: `EntityCatalogGraphCard` — карточка «directly related entities» на странице сущности с фильтрацией по типам связей; `CatalogGraphPage` — standalone-вьюер «to navigate through the entities and filter for specific relations»; `EntityRelationsGraph` — headless-компонент для сборки кастомных графов [18]. Модель типов связей подключаемая per-installation: `DefaultCatalogGraphApi` принимает `knownRelations`, направленные пары `knownRelationPairs` и `defaultRelationTypes: { exclude | include }` — кастомные типы связей можно скрыть из дефолтной выборки [18]. Панель фильтров страницы — семь контролов: MaxDepth, SelectedKinds, SelectedRelations (типы связей), Direction, Curve, unidirectional («simplified»), mergeRelations [19]. Drilldown-семантика: клик по узлу **пере-кореняет граф** на этом узле, shift+клик уводит на страницу сущности; оба действия инструментированы через analytics [19]. `initialState` страницы — типизированный декларативный конфиг (rootEntityRefs, selectedKinds, selectedRelations, maxDepth, direction, unidirectional, mergeRelations, curve, showFilters) [19]. Ядро рендера — core-components `DependencyGraph`: `dagre.layout()` + d3-zoom/d3-selection поверх одного SVG [20][33]; zoom `scaleExtent([1, Infinity])` — только внутрь (нельзя отдалиться ниже 100%), pan зажат в bounding box графа [20]. Публичная поверхность layout-параметров обширна: `direction` (dagre `rankdir`, TOP_BOTTOM по умолчанию), `align`, node/edge/rank margins (50/10/50), `acyclicer: 'greedy'`, `ranker: NETWORK_SIMPLEX`, `labelPosition`, `edgeRanks/edgeWeight`, `fit: 'grow'|'contain'`, варианты кривых, `showArrowHeads` (по умолчанию **false**), fullscreen [20]. Кастомизация — фабрики `renderNode/renderEdge/renderLabel` [20]; лимита числа узлов в коде нет, но и click-to-highlight/hover-highlight в ядре нет — интеракция добавляется через onClick внутри renderNode [20].

**Ardoq (primary docs, свежие 2026).** Каталог из **16 view-типов out-of-the-box**: Block Diagram («a very generic view to display any kind of graph data»), Dependency Map, Component Matrix, Pages, Tagscape, Component Tree, Dependency Wheel, Treemap, Relationships («complete overview of all relationships in the workspaces or the given context»), Swimlanes, Tables, Reference Table, Dependency Matrix, Spider Chart, Capability Map, Bubble Chart [21]. Отдельного «Graph view» нет — графовые данные рендерятся выбором view-style внутри viewpoint (Block diagram / Dependency map / Relationships / Timeline) [24][26]. Dependency Map: контекстный компонент сверху, иерархические потомки — квадратные узлы, referenced — скруглённые; **раздельные слайдеры входящих/исходящих степеней** обхода; цепочки строго направленные — смена направления внутри цепочки не отображается, для этого случая Ardoq рекомендует Block Diagram; загрузка скоуплена воркспейсом («Ardoq only loads components which are directly referenced from a loaded workspace» — много-степенный обход молча теряет ветки закрытых воркспейсов) [22]. Контролы карты: Show Only Connected Components, Vertical/Horizontal layout, Color by Reference Type, Include Reference Parents (dotted border, слияние общих предков), Collapse Groups/Hierarchy слайдер [22]. Интеракция: hover подсвечивает все вхождения компонента, left-click → навигация к компоненту (при необходимости открывает воркспейс), right-click → контекстное меню; детерминированная сортировка связей: направление (incoming first) → тип связи → navigator sort → алфавит [22]. Perspectives поверх карты — сохранённая конфигурация: conditional formatting, labelling (например, тип связи как label узла), покраска узлов по числовому полю (пример: total direct cost) [22]. Block Diagram traversal: верхний дропдаун степеней + advanced раздельные in/out; обход останавливается на путях, нарушающих выбранное направление; при нуле степеней остальной граф гасится (faded out) [23]. Viewpoint = персистентный объект: «Save as viewpoint» хранит имя + все конфигурации («ensuring everyone sees the information exactly as you intended»), viewpoint'ы шарятся org-wide; один датасет — переключение view-стилей поверх него; общий слой опций (grouping, conditional formatting, label formatting) действует на все стили; правки из view («See component details → Open new dataset») видны мгновенно; сохранение viewpoint заблокировано при нескольких открытых датасетах [24]. Dependency Matrix — инструмент **массового создания** связей (источники слева, targets сверху, клик по пересечению → создать reference + выбрать свойства, cross-workspace создание), анализ не заявлен [25].

**LeanIX (Wayback 2021, medium).** Единственный найденный предвычисленный impact-механизм: статус «Aggregated Obsolescence Risk» считается **рекурсивным обходом активных связей** — Application наследует риск от IT Components (relApplicationToITComponent) и рекурсивно через relToChild/relToRequires (набор связей конфигурируется); диспозиция риска («accepted»/«addressed» + комментарий) хранится на самой связи Application–IT Component [27] (2021 snapshot — продукт эволюционировал). Отдельных экранов relationship-graph / «Interactive Explorer» / what-if в архивной документации GitBook-эры нет: среди ~150 slug'ов ни один не совпадает с relationship|graph|impact|explorer|what-if [28] — impact-анализ существовал как агрегатные report-раскраски поверх инвентаря, а не как отдельный граф-экран [27].

**Граф-библиотеки (GitHub, accessed 2026-10-04).** cytoscape.js: 11.2k★, MIT, v3.34.3 (2026-09-07), заявленный cadence «feature releases are made monthly, while patch releases are made weekly» [29]. sigma.js: 12.2k★, MIT, WebGL-библиотека «aimed at visualizing graphs of thousands of nodes and edges… built on top of graphology», v4 — beta (beta.6, 2026-09-16) [30]. react-force-graph: 3.3k★, MIT, v1.48.3 (2026-09-29); четыре React-компонента (2D Canvas, 3D WebGL, VR/AR), физика d3-force-3d, DAG-режимы (`dagMode` + `onDagError` для циклов), стрелки и движущиеся частицы по связям, zoom 0.01–1000, perf-переключатели `autoPauseRedraw`/`enablePointerInteraction`, готовые примеры «click to focus» и «click to expand/collapse» [31]. @xyflow/react (React Flow): 38.6k★, MIT, v12.12.0 (2026-09-24), но организационное использование — через «React Flow Pro» (платно) или GitHub Sponsors [32]. Backstage при этом не использует ни одну из них — dagre + d3 в core-components [33].

**Синтез D2 — паттерны для структуры экранов:**

1. Три поверхности графа (паттерн Backstage): виджет-окрестность на карточке сущности, standalone-страница графа с фильтрами, headless-компонент для кастомных графов [18].
2. Стандартный control-bar графа: depth, direction, типы связей (чипы с safe-defaults через exclude), unidirectional/merge — конвергенция фильтров Backstage и слайдеров in/out degrees Ardoq [19][22].
3. Drilldown = re-root, не модалка: клик пере-кореняет граф, клик с модификатором уводит на карточку сущности [19][22].
4. Прогрессивное раскрытие вместо полного графа: faded-out остального графа, collapse-hierarchy слайдер, show-only-connected, zoom-in-only с clamp pan [20][23].
5. Сохранённая конфигурация графа — first-class: персистентный объект (Ardoq viewpoint) либо сериализуемый декларативный initialState (Backstage → shareable URL) [24][19].
6. Impact-анализ в референсах — интерактивная traversal-семантика (степени/направление/типы связей); предвычисленный агрегат — редкость (LeanIX Obsolescence Risk: рекурсивный обход активных связей, диспозиция хранится на связи) — полезная идея «наследуемых статусов» для метамодели из 20 типов связей [22][27].
7. Matrix — editing-режим (массовое создание связей), не аналитика; позиционировать отдельным режимом работы со связями [25].
8. Обход должен идти по хранилищу, а не по загруженному датасету — workspace-scoped loading Ardoq молча теряет ветки [22].
9. Выбор рендера: SVG + dagre достаточно для Backstage-масштаба каталога; WebGL (sigma.js) / Canvas (react-force-graph) — для тысяч узлов; xyflow лицензионно неудобен для org-use [30][31][32][33].

## D3. Дорожные карты развития продуктов

**Ardoq (primary docs, свежие 2026).** Дорожная карта строится не отдельным объектом, а двумя механизмами. Первый — **Timeline View**: компоненты — строки (вертикальный список или иерархия по grouping rules); значения полей типа Date Range рендерятся как **бары (фазы)**, значения полей типа Date — как **ромбы (milestones)**; несколько date-range на одном компоненте = несколько фаз; иерархия с expand/collapse [38]. Поля создаёт Admin/Writer: «Date Range» (рендерится как фаза, имя поля = имя фазы) vs «Date» (milestone), ввод через Grid Editor как start+end пара [38]. Конфигурация: show/hide фаз и milestones через пикеры, окно видимости start/end date, layout'ы daily/weekly/monthly/quarterly/yearly с минимальными окнами (≥1 неделя / 1 месяц / 3 месяца / 1 год / 3 года) плюс auto-layout, кнопка Today, zoom, hover-detail [38] (верифицировано: live-страница подтверждает bars/milestones/мин-окна дословно). В июне 2026 добавлены multiple labels на строку (из default/custom полей, per-type show/hide имён полей, >2 строк — обрезка с hover-tooltip), expand/collapse по labels/иерархии/группам, hover подсвечивает строку, клик — sticky highlight; всё сохраняется в viewpoint [39]. Заявленные use case'ы: Application Lifecycle Management, IT-lifecycle Management, Strategy to Execution [38]. Модель lifecycle: ordered enum-поле «Lifecycle Phase» (Evaluation → Implementing → Live → Phasing out → Retired) + date-range на каждую фазу; конец фазы должен совпадать с началом следующей, но разрывы допустимы; продвинутый набор добавляет Evaluation/Development/Live/Mainstream (Mainstream = суб-фаза Live); минимум = Lifecycle Phase + Live; рекомендован единый standardized набор полей на всех типах компонентов/связей; сбор данных — Surveys с Broadcasts на владельцев приложений; ALM с 2025-09-11 входит в Ardoq Foundation [40]. Второй механизм — **Scenarios**: одна дорожная карта = сценарий на каждую фазу проекта (пример Skype-for-Business→Teams: Integration / Migration / Retirement); сценарий — «temporary branch off the current state», планируемые изменения не трогают mainline; внутри сценария заводится Project-компонент + Project Phase Components, соединённые с затрагиваемыми системами, с proposed start/end датами — тогда таймлайн показывает затронутые системы на фазу, start/stop фаз и milestones; есть visual difference для дельт фаз [41]. Жёсткое ограничение (вербатим, верифицировано): «Currently, Scenarios support Block Diagram and Pages view styles only» — нативного scenario-timeline нет [41]. Governance-крючок: поле «Application Roadmap URL» на типе Application + dashboard-виджет приложений без roadmap [41]. Квартальная сетка как колонки данных — workaround, не фича: Calculated List Field «Quarter-Year» (Gremlin от live_end_date) колонкой в Component Matrix [44]. Демо-слой — Presentations: слайды = живые view и дашборды (всегда актуальны, обновление через «replace slide with current view»), shareable link с уровнями доступа вплоть до «anyone with URL» (public mode включается поддержкой), embed в SharePoint/Confluence; **Explore mode**: double-click по компоненту в слайде динамически пере-контекстуализирует view (отключаемо per-presentation и org-wide); гоча: слайд видит только компоненты воркспейсов, открытых на момент создания слайда [42]. Jira Software Cloud: импорт Projects/Epics/Stories/Tasks/Bugs/Issues/Users/Ideas с полями вкл. start/end date-time; только Jira Cloud, лимит <5000 объектов, без экспорта, pull ≤1 раза в день; как импортированные тикеты рендерятся на timeline — не документировано [43].

**SAP LeanIX (маркетинг-регистр, medium; страница ©2026 SAP SE).** Модуль Architecture and Road Map Planning организует планирование в три пилона: «Design your target architecture», «Plan your transformation journey», «Govern your transformations» [34]. Milestones — first-class объекты: «visual reference points on roadmaps», консолидируются в сводном виде по всем project-отчётам, шарятся и переиспользуются между связанными проектами и суб-проектами, а обновление даты milestone автоматически отражается везде, где он используется [34] (корроборировано round 1–2, верифицировано live-страницей). Impact проекта на ландшафт показывается «at completion and at key milestones», планируемые изменения автоматически раскладываются на детальные impacts, категоризуемые по типу [34]. List-view всех transformations: зависимости, go-lives, filter/focus, inline editing и bulk actions [6][34]. Интеграции: Jira-синк epics/to-dos/issues из множества проектов и инстансов в initiative fact sheets; синк проектов из SAP Cloud ALM [34]. Lifecycle-данные IT Components: Lifecycle Catalog (2022 snapshot) — vendor-maintained провайдерские данные с enum Plan → Phase-in → Active → Phase-out → End-of-life → End-of-sale с датами, successor-версиями и support-политиками, синхронизируется в fact sheets [35].

**Backstage.** Экосистема практически пуста: GitHub-поиск «backstage roadmap» = 3 репозитория, единственный релевантный — rothenbergt/backstage-roadmap-plugin (11★, 2 forks, создан 2024-10-04, push 2026-09-07); «backstage quarterly planning» = 0 [36]. Плагин — **status-column board, не timeline**: колонки Suggested / Planned / In Progress (скрыта по умолчанию) / Completed / Declined; модель данных без дат и кварталов — status, votes, comments, author, reorder [37]. Фичи: voting, threaded comments, форма с duplicate detection при вводе, deep link `/roadmap?feature=<id>` открывает detail drawer, datasources — БД плагина или GitLab issues [37]. Продуктовое чтение: это feedback/engagement-борд, а не EA planning timeline [37].

**Синтез D3 — паттерны для структуры экранов:**

1. Два архетипа «roadmap» сосуществуют: time-based swimlane timeline (Ardoq) vs status-column board (единственный Backstage-плагин) — для EA-дорожной карты ИТ Ландшафта нужен timeline; борд — другой продукт с другим назначением [38][37].
2. Фазовая модель данных — примитив метамодели: ordered enum + date-range per phase на той же сущности; бары = date-range, ромбы = date — ложится прямо на lifecycle-поля v1.5 [38][40].
3. Milestones — отдельный визуальный класс (ромбы) и отдельные first-class объекты с cross-project переиспользованием и auto-propagate даты (LeanIX) [34][38].
4. Дорожная карта = ветка данных, а не изменение mainline (Ardoq Scenarios: «temporary branch off the current state») — целевое состояние планируется изолированно [41].
5. Антипример: Scenarios не поддерживают timeline-стиль (только Block Diagram и Pages) — roadmap-экран нельзя строить как побочный эффект scenario-ветки; timeline должен быть first-class поверх данных [41].
6. Привязка к сущностям идёт через связи: Project Phase Components соединяются с затрагиваемыми системами — экран roadmap в v1.5 строится поверх связей initiative→сущности (impacted-системы на фазу) [41].
7. Демо-слой для команд: presentation shell над живыми view (не скриншоты), shareable/embeddable ссылки, explore-mode с пере-контекстуализацией по клику [42].
8. Квартальная гранулярность оси нативна в Ardoq Timeline (daily…yearly, quarterly требует ≥1 год данных); «квартальная дорожная карта» как колонки данных — workaround (2023); в Backstage-экосистеме quarterly planning отсутствует полностью (0 плагинов) [38][44][36].
9. Lifecycle-каталог с внешними данными провайдеров (LeanIX: 6-фазный enum с датами, successor-версии, support-политики) — кандидат на справочник в v1.5 [35].

## D4. Тех-радар, связанный с продуктами

**ThoughtWorks (эталон формата).** Радар = 4 квадранта (Techniques, Platforms, Tools, Languages & Frameworks), элементы — «blips» [45]. Актуальный набор колец — Adopt, Trial, Assess, **Caution**: четвёртое кольцо переименовано из Hold в Caution в релизе BYOR v1.2.0 («Merge PR #412, which involves rename of 'Hold' ring to 'Caution'», верифицировано по tag-странице), при этом веб-копия TW до сих пор пишет «Hold» — веб отстаёт от кода [46]. Семантика изданий: blip, не сменивший кольцо, выпадает из следующего издания; радиальная позиция внутри кольца значима (близость к границе со следующим внутренним кольцом = растущая уверенность); опциональный статус New / Moved In / Moved Out / No Change; публикация дважды в год как интерактивный сайт + PDF [45]. Официальный генератор build-your-own-radar (AGPL): данные = Google Sheet / CSV / JSON ровно с колонками name, ring, quadrant, isNew, description; онлайн ровно 4 квадранта и 4 кольца, кастомные имена — только в self-hosted; позиции blip'ов игнорируются [46][47].

**Backstage (schema.ts — верифицировано field-for-field).** Плагин перенесён в backstage/community-plugins (workspace = frontend + backend + common), «inspired by Zalando's Tech Radar» [48]. Модель данных (zod-схема): RadarEntry {key, id, quadrant, title, url? (deprecated в пользу links), timeline[], description?, links?[]}; RadarEntrySnapshot {date, ringId, description?, moved? ∈ {-1 Down, 0 NoChange, 1 Up}}; RadarQuadrant {id, name}; RadarRing {id, name, color, description?}; TechRadarLoaderResponse {quadrants («Should be 4»), rings, entries} — **sizes/angles в схеме нет**: геометрия вычисляется на рендере из quadrant+ring [49] (sample-данные корроборируют: 4 кольца с hex-цветами, timeline reverse-chronological). Подача данных: backend грузит JSON по URL через URL Reader (`techRadar: { url }` в app-config, авторизация в приватные репо через integrations) либо кастомный `TechRadarApi`, биндится на `techRadarApiRef`; несколько радаров — через prop `id` [48][50].

**AOE (v4).** Репозиторий переименован: aoe_technology_radar редиректит на **AOEpeople/techradar**; v4.0.0 — полный rewrite на Next.js SSG, визуализация без D3, fuzzy search на Fuse.js, non-overlapping blips, переработанный tag-фильтр [51] (верифицировано частично: репо techradar живо, MD+frontmatter подтверждён; v4/Next.js/Fuse трассируются к README aoe_technology_radar). Авторинг — **Markdown + YAML front-matter** (title, ring, quadrant, tags, featured), релизы = папки YYYY-MM-DD под `./radar`, имя .md-файла = идентификатор элемента; **история выводится из структуры папок**: перезапись файла в новом релизе мержит атрибуты и создаёт history-entry; JSON — build-артефакт (`npm run build:data` → data.json), не авторский формат [52]. config.json ведёт всем отображением: quadrants/rings {id, title, description, color, radius, strokeWidth}, флаги new/changed, тогглы showSearch/showChart/showTagFilter/…, порядок секций radar/tags/list, опции Fuse.js, chart.size для плотных радаров, editUrl с плейсхолдерами {id}/{release} [52]. Лицензия Apache-2.0 — на код генератора, не на статьи [52].

**SAP LeanIX (маркетинг-регистр, medium).** «Tech Radar reports help you broadcast adoption standards to development teams» — радар как генерируемый report поверх инвентаря, а не отдельный silo [53]. Use case Obsolescence Risk: приложения связаны с infrastructure-слоем, EOL-компоненты выявляются на инвентаре, lifecycle-данные приходят из reference catalog и агрегируются на уровне приложений, remediation — accept-or-address per application owner, есть technology upgrade roadmaps, популяция инвентаря через ServiceNow CMDB [53][54].

**Связь радара с инвентарём.** Сквозной негативный результат: **ни один референс не связывает элементы радара с инвентарём автоматически** — TW BYOR вообще не имеет url-колонки [47]; Backstage ограничивается outbound `url`/`links` на элемент, а backend не запрашивает каталог [48][49]; AOE — статический генератор без инвентаря [51][52]. LeanIX — ближайший аналог: радар как report поверх связей Application↔IT Component [53]. Точки расширения для «радара, связанного с продуктами» (анализ поверх источников, не факт): (a) per-entry link → страница инвентарного запроса; (b) кастомный API-слой, джойнящий элементы радара с отношениями инвентаря на read-time (паттерн LeanIX) [47][48][53].

**Синтез D4 — паттерны для структуры экранов:**

1. Модель данных радара стабилизировалась: quadrants[] / rings[] / entries[] с timeline[{date, ringId, moved}] — позиции (sizes/angles) нигде не являются данными, вычисляются на рендере → радар в v1.5 = чистые данные + рендер [49][52].
2. История движения — first-class: dated timeline с moved ∈ {-1,0,1} (Backstage), merge-on-release (AOE), drop-off между изданиями (TW) [49][52][45].
3. Авторинг — git-hosted декларативные файлы: AOE md+frontmatter в release-папках, Backstage JSON в репо через URL Reader, TW Sheet/CSV/JSON → для ИТ Ландшафта радар естественно живёт в GitLab-зеркале рядом с YAML/MD сущностей [52][48][47].
4. Радар должен быть report поверх инвентаря (паттерн LeanIX, которого нет у TW/Backstage/AOE): элемент радара = сущность Технология с deep-link в отфильтрованный список приложений (join по связи runs-on/реализуется-через) [53].
5. Кольца/квадранты — data-driven конфиг (имена, цвета, radius/strokeWidth), не код; новые кольца — изменение конфига [52][49][47].
6. При заимствовании семантики колец опираться на release notes, не на веб-копию (Hold→Caution расхождение), и не на sample-данные Backstage (там до сих пор «hold») [46][49].
7. Поиск по радару — fuzzy (Fuse.js), фильтрация по тегам — отдельное поле tags в авторинге [52].

## D5. ADR / HLD / RFC, связанные с продуктами

**Backstage (source-verified).** TechDocs — «docs-like-code» на MkDocs: инженеры пишут Markdown «который живёт вместе с кодом»; в Spotify 5000+ doc-сайтов и ~10k просмотров в день; документация обнаруживается «from the Service's page in Backstage Catalog»; поиск по документации — first-class фича; хранение генерированных статических сайтов — local FS / GCS / S3 / Azure / Swift, исходники — в код-репо (поддерживаемые хосты включают GitLab); привязка к сущности — аннотация `backstage.io/techdocs-ref: dir:.` (или `url:` для документов вне код-репо), автономные doc-сущности — `spec.type: documentation` [55]. ADR-плагин `@backstage-community/plugin-adr` (workspaces/adr, 4 пакета: adr, adr-backend, adr-common, search-backend-module-adr) активен — последние коммиты в workspace 2026-09-24 («Version Packages», миграция MUI→BUI) [56]. Связывание с сущностью — аннотация `backstage.io/adr-location` (путь относительно catalog-info.yaml или абсолютный URL к папке с ADR-md), таб `/adrs` рендерится только когда аннотация разрешается (`if={isAdrAvailable}`); дефолтный парсер покрывает MADR 2.x (2.1.2) и 3.x (3.0.0) — front matter распознаётся только в 3.x-форме; фильтр файлов по умолчанию — regex `/^(decided-adrs\/)?\d{4}-.+\.md$/` (NNNN-title); контент-декораторы переписывают относительные ссылки/embeds и форматируют front matter [56]. Поиск: коллатор индексирует ADR в Backstage Search как типизированный результат `'adr'` (AdrDocument + AdrSearchResultListItem + фильтр «Architecture Decision Records» в сайдпанели) [56]. New Frontend System: alpha-экспорт с декларативными extension points `entity-content:adr/entity`, `search-result-list-item:adr`, `api:adr/adr-api` [56]. Принципиально: **каталог не хранит тела документов** — TechDocs хранит только сгенерированные сайты, source-of-truth Markdown остаётся в репо; каталог работает как index/renderer/linker (аннотация → read-time fetch → таб сущности + типизированный поисковый коллатор) [55][56].

**MADR и процессы-референсы.** MADR v4.0.0 (2024-09-17) — де-факто стандарт структуры ADR: YAML front-matter (status, date, decision-makers, consulted, informed) + секции Context and Problem Statement, Decision Drivers, Considered Options, Decision Outcome («Chosen option: X, because…»), Consequences, Confirmation, Pros and Cons; статус — свободное поле с конвенцией supersede «superseded by ADR-0123»; именование `docs/decisions/NNNN-title-with-dashes.md`; крупные проекты подпапками по категориям с локальной нумерацией [57]. PEP 1: статус-enum Draft / Active / Accepted / Provisional / Deferred / Rejected / Withdrawn / Final / Superseded; парный supersede — заголовки `Replaces` / `Superseded-By`; после резолюции PEP — исторический документ [58]. Rust RFCs: RFC = Markdown, влитый в репо, номер = номер PR; Final Comment Period 10 дней с disposition merge/close/postpone; каждый принятый RFC получает tracking issue на имплементацию; существенные изменения = новый RFC с пометкой в оригинале [59]. AWS Prescriptive Guidance: Proposed → Accepted/Rejected; принятый ADR иммутабелен («Changes to an existing ADR requires creating a new ADR»), на acceptance добавляются timestamp/version/stakeholders; decision log используется в code reviews (ревьюер делится ссылкой на ADR); скоуп ADR — структура, NFR, зависимости, интерфейсы [60]. log4brains (1.6k★, Apache-2.0) спит с 2024-12-17 (~22 месяца) — устаревший вариант; характерные практики: без принудительной нумерации (date-based имена против git merge-конфликтов), метаданные «автоматически угадываются» из raw text + git logs [61]. JPH architecture-decision-record (17.1k★, README 2025-05-29) — контраст: предпочитает дескриптивные безномерные имена (`choose-database.md`), один decision на ADR, supersede через новый ADR; в репо — каталог архитектурных диаграмм, привязанных к application components (C4 Context/Container TO-BE/AS-IS, ERD, BPMN, RBAC-роли) [68].

**HLD.** Сквозной негатив трёх раундов: **«HLD» не стандартизирован** — термин отсутствует во всём первичном контенте arc42, C4 и Structurizr [62]. Ближайшие формальные аналоги: **arc42** — шаблон архитектурной документации из ровно 12 секций (01 Introduction and Goals, 02 Constraints, 03 Context and Scope, 04 Solution Strategy, 05 Building Block View, 06 Runtime View, 07 Deployment View, 08 Crosscutting Concepts, 09 Architecture Decisions, 10 Quality Requirements, 11 Risks and Technical Debt, 12 Glossary), лицензия CC BY-SA 4.0 [63]. Секция 03 привязывает документ к одной системе: «delimits your system … from all its communication partners … thereby specifies the external interfaces» — с практическими tips «Explicitly demarcate your system from its environment», агрегировать соседние системы, «Show all (all!) external interfaces» [63]. Секция 09 «Architecture Decisions» — first-class секция шаблона: ADR живут внутри архитектурного документа системы [63]. **C4**: иерархия абстракций (software systems, containers, components, code) и диаграмм; собственное руководство по скоупу: «the system context and container diagrams are sufficient for most software development teams» (верифицировано на c4model.com/diagrams) — т.е. HLD-уровень = landscape/context/container, component/code — LLD [64]. **Structurizr**: DSL создаёт «multiple software architecture diagrams from a single model» — элементы и связи определяются один раз, диаграммы выводятся (reference implementation C4, export в PlantUML/Mermaid/HTML) [65]. Интерпретация для маппинга (синтез, medium): HLD ≈ arc42-секции 01–04 + black-box уровень 05 + 09–12 [62][63]. Фоновая практика (2020, старше окна свежести — treat as background): design docs Google — Context and scope / Goals and non-goals / Actual design (system-context diagram, APIs, data storage) / Alternatives considered / Cross-cutting concerns, 10–20 страниц, lifecycle creation→review→implementation→maintenance [66].

**Синтез D5 — паттерны для структуры экранов:**

1. Каталог не хранит тела документов — Backstage хранит аннотации (`techdocs-ref`, `adr-location`) и рендерит на read-time; в v1.5 сущности ссылаются на MD в GitLab (зеркало уже предусмотрено метамоделью), каталог = индекс/рендерер/линкер [55][56].
2. ADR = guarded таб на карточке сущности (таб виден только при наличии аннотации) + типизированный поисковый коллатор с фильтром в сайдпанели поиска [56].
3. Жизненный цикл документа — статусный enum: ядро proposed/accepted/rejected (+draft) сходится у PEP/MADR/AWS/Rust; supersede — парные ссылки (Replaces/Superseded-By, «superseded by ADR-0123») → в метамодели ADR — сущность со статус-полем и связью supersede [57][58][60][67].
4. MADR 4.0.0 — эталон структуры ADR, но Backstage-плагин парсит только 2.x/3.x: либо pinned MADR 3.x, либо свой парсер [56][57].
5. HLD не стандартизирован — за основу брать arc42 (12 секций; Section 03 привязывает документ к системе и её внешним интерфейсам) либо C4 (context+container достаточны для HLD-уровня) [63][64].
6. Одна модель → много диаграмм (Structurizr): диаграммы сущности — проекции метамодели, а не отдельные хранимые артефакты [65].
7. Нумерация: NNNN-title (MADR/Backstage/adr-tools) vs date-based (log4brains) vs from-PR (Rust) — для v1.5 естественен NNNN-title в папке сущности поверх business_id [67].
8. RFC-процесс heavyweight (FCP, tracking issues) оправдан только при стандартизации; минимум для v1.5 — статус + даты + авторы + supersede-связи [58][59].

## D6. Поиск по любым атрибутам и описаниям

**Ardoq (primary docs, 2026, верифицировано).** Поиск двухуровневый. Уровень 1 — **semantic quick search в GA** (июль 2026, rollout по организациям через CSM): находит components, dashboards, reports, surveys, presentations, broadcasts «by what they mean, not just the words you remember» — natural-language фразы («source control tool for development») матчат элементы, чьи имена не содержат слов запроса [69]. Индексируются ровно **6 типов** (Component, Dashboard, Report, Survey, Presentation, Broadcast); workspaces, viewpoints, references и отдельные поля не индексируются; ниже порога релевантности — expandable «Other results» [69]. Поиск **permission-aware**: недоступные элементы не появляются даже при сильном матче [69]. В поле поиска — inline filter chips (по типу или admin-configured quick-filter типам компонентов) и кнопка Filter → переход в Advanced Search [69]. **ID-first search**: точный component key или значение admin-designated «custom search field» (внешний ID / cost centre) пиннится наверх результатов — оба case-insensitive и работают с частичными значениями [69]. Поисковая строка = **command palette**: ⌘/Ctrl+K, «/» переключает в command mode, empty-state показывает «Currently Open» для быстрого возврата [69]. Admin-настройки поиска: тумблер semantic search (off → «falls back to classic keyword search» по name/description), выбор custom search field, тумблер Ardoq ID search, quick-filter типы [69]. Semantic search поддерживает 100+ языков («results are best when your query and the content are in the same language»), embedding/ranking на инфраструктуре Ardoq без third-party AI; индексация near-real-time («within a short while»); в legacy Discover нет; search history и saved searches ещё не реализованы [69]. Уровень 2 — **Advanced Search**: декларативный rule builder (components/references → field → operator), правила и subqueries комбинируются ALL/ANY, enum multi-select, проверка отсутствия значения («don't have a Criticality value»), workspace scoping; сохранённые запросы снапшотятся еженощно (история для дашбордов); экспорт .xls/Excel/JSON; точки входа — Analytics → Advanced search и первый шаг Report Builder [70]. Power-user уровень — **Gremlin Graph Search**: traversal-язык по графу, требует привилегии «Create Gremlin» с явным security warning (Writer видит данные всего графа в обход workspace permissions); запросы персистятся только как Reports; зарезервированные поля живут в одном namespace с пользовательскими (OID, component-key, created, last-updated, rootWorkspace, label()); примеры — агрегации, enum-фильтрация, missing-relationship, транзитивный impact (`repeat(timeLimit(20).both().simplePath())`), теги [71]. **Data Inventory** — табличный browse-all-entities экран поверх графа (vendor: «snappy» с «hundreds of thousands of components»); discovery — **multi-column фильтры-чипы, а не текстовый поиск**: фильтр по любому отображаемому свойству, removable chips над таблицей, sort по любой колонке; колонки/порядок персистятся per user; references рендерятся колонками с типом и направлением («→ Is Supported By →»); inline-редактирование (Enter/Esc), multi-row paste ≤100 строк, drag-fill, merge, drag-and-drop reparent в иерархии; undo нет; «Upcoming» обещает contains/starts-with/numeric-range — substring-фильтров сегодня нет [72] (верифицировано по живой статье).

**Backstage (верифицировано по README).** Три движка из коробки: Lunr (in-memory, zero-config, «highly discouraged» для продакшена), **Postgres**, Elasticsearch/OpenSearch (ES ≥8.19, ES 7 снят с поддержки) [73]. PG-движок — first-party `@backstage/plugin-search-backend-module-pg` (в монорепо), требует PG ≥ 12, заявлено «performs well with ten thousands of indexed documents»; подсветка маппится 1:1 на `ts_headline` с тумблером `useHighlight: false` (docs предупреждают о «potentially impact performance») [74]. Архитектура: `SearchEngine` + `QueryTranslator` (абстрактный запрос = terms + filters + types); документ — минимум title, text, location; **один index на document type**; коллаторы — стримы документов, декораторы — transform-стримы; индексы пересобираются целиком по расписанию (explicit non-goal: incremental/event-driven indexing); search page — app-owned, плагин владеет состоянием через search context; `<SearchBar/>/<SearchFilter/>/<SearchResult/>` комбинируются, кастомные result items — через `SearchResultListItemBlueprint` с predicate по `result.type`, кастомные фильтры — `SearchFilterBlueprint` [73]. Facet counts (агрегированные счётчики в Solr-смысле) в документированном компонентном наборе отсутствуют [73].

**PostgreSQL (документация PG18; фичи есть в PG16).** `jsonb_to_tsvector(config, document, filter)` документирован (Table 9.43): фильтр — jsonb-массив ключевых слов «string»/«numeric»/«boolean»/«key»/«all»; позиции генерируются как будто элементы разделены одним стоп-словом; document order jsonb-полей — implementation-dependent (верифицировано) [75]. Документированный паттерн: **stored generated tsvector колонка + GIN** (`ADD COLUMN … tsvector GENERATED ALWAYS AS (to_tsvector(...)) STORED`) — быстрее выражений, но дороже по диску; в expression index допустим только two-argument `to_tsvector` с явным конфигом [75][76]. `websearch_to_tsquery` безопасен для сырого пользовательского ввода — «will never raise syntax errors» (кавычки = фраза, `or`, `-` = NOT; weights/prefix не умеет) [76]. Ранжирование: `setweight(tsvector,'A'..'D')` + `ts_rank_cd` с весами {D,C,B,A}={0.1,0.2,0.4,1.0}; docs предупреждают — ранжирование «can be expensive… I/O bound»; `ts_headline` — output «not guaranteed to be safe for direct inclusion in web pages» (XSS caveat) и работает по оригинальному документу, «so it can be slow» [76]. Языки: predefined text-search configurations «for many languages», полный список даёт `\dF`; документация сама исполняет `ALTER TEXT SEARCH CONFIGURATION russian …` без создания конфига — свидетельство, что `russian` поставляется встроенно (medium — enumerация на живом PG16 в этом прогоне не выполнена); Snowball-словари встроены per language; LIKE/regex — «no linguistic support», без ranking и index support [77].

**Essential и LeanIX.** У Essential выделенного текстового поиска нет: features-страница документирует только Query — «query wizard» (OS) и **Dynamic Query Tool v2** (beta): декларативный attribute-query builder (выбор класса → result fields с sort/width/Navigate/Repeat fan-out → вложенные AND/OR → date-условия), результаты сохраняются как Query/Catalogue (персистентные классы репозитория) с import/export между репозиториями; в university sitemap нет ни одного slug со «search» [78]. LeanIX (2021 snapshot, medium): инвентарные фильтры — lifecycle из 6 статусов + режимы Point-of-Time (Today/End of Month/…) и Time-Frame (effective/starts/ends within); Advanced Filter работает через связанные типы FS («triangular» filtering: Applications, связанные с Data Objects, тегированными PII); tag set logic — at-least-one / all / none [79].

**Синтез D6 — паттерны для структуры экранов:**

1. Два уровня поиска: быстрый omnibox (⌘K: semantic + keyword fallback, ID-first pinning, permission-aware, filter chips) + декларативный Advanced Search (rule builder field→operator, ALL/ANY, subqueries, missing-value, enum multi-select) — конвергенция Ardoq [69][70].
2. Permission-aware фильтрация — в самом поиске, не пост-фильтрация UI [69].
3. ID-first search с admin-настраиваемым «custom search field» — у v1.5 роль такого поля выполняет business_id (PREFIX-slug) [69].
4. PG-native стек достаточен при ≤20k сущностей: stored generated tsvector + GIN поверх jsonb_to_tsvector и setweight(name, description), парсинг ввода — websearch_to_tsquery, ранжирование — ts_rank_cd; external engine не оправдан; индексация через generated columns синхронна и не требует scheduler [74][75][76].
5. ts_headline — опциональная и небезопасная подсветка: sanitize на клиенте, тумблер useHighlight:false по паттерну Backstage [74][76].
6. Facet counts в Backstage-компонентах отсутствуют — считать агрегаты GROUP BY по тем же JSONB-выражениям на бэкенде [73][75].
7. Табличный инвентарь — discovery фильтрами-чипами по колонкам, текстовый поиск — отдельный omnibox; substring/range-фильтры (у Ardoq «Upcoming») заложить сразу [72].
8. Русский язык: `russian` конфиг, судя по docs, встроен, но подтвердить `\dF` на живом PG16 до дизайна схемы tsvector-колонок [77].
9. Gremlin-стиль power-user traversal (транзитивный impact, missing-relationship) — в v1.5 реализуется параметризованными traversal-эндпоинтами, не сырым языком запросов [71].
10. Сохранённые запросы — first-class (Ardoq: nightly snapshots для истории, Essential: Query/Catalogue как классы репозитория); у Ardoq saved searches в omnibox ещё нет — для v1.5 сделать сразу [70][78][69].

## D7. Декларативная и модульная конфигурация UI

**Ardoq (primary, верифицировано).** Component Overview метамодель-driven вплоть до layout: порядок полей наследуется из workspace manager («Field order on the Component Overview Page follows the order set in the workspace manager»); Priority Fields — admin per тип (Organization Settings → Priority settings; без конфигурации секция скрыта); References-таб наполняется из разрешённых троек метамодели **включая zero-instance** («This is by design, so you can create new references of any allowed type») [80] (верифицировано по живым статьям). Field Groups (beta, 2026-08-25): admin бандлит поля в подписанные секции под **My Organization > Fields/Metamodel Constraints** — конфигурация групп живёт в одной админ-зоне с ограничениями метамодели; группы centrally managed, type-scoped, flag-gated per org; без групп поля — плоский алфавитный список [80]. Фиксированный код при этом: 5-таб shell карточки, набор визуализаций, редакторы выбираются по типу поля, calculated fields read-only (Gremlin), привязка priority viewpoints к типу — admin-конфиг; Styles — данные на сущности (250+ иконок вкл. ArchiMate/BPMN/EDGY) [80]. Задокументированные ограничения: нет audit-log таба, нет inline-editing на Overview, длинные списки permitted triples, замедление на сотнях references [80]. **Perspectives** — слой end-user конфигурации (не только admin): фильтрация/группировка/условное форматирование поверх view; Manage-окно с тремя зонами (Filters, Grouping, Formatting); Quick Filters внизу Navigator перечисляют присутствующие в view компоненты и типы связей; Saved Perspectives именуются и шарятся; workspace default perspective назначается admin'ом через свойства воркспейса [81]. Редактирование метамодели — внутри продукта: статьи «Manage Component Types and Metamodel», «How to Edit a Metamodel», «In-view data modeling» (beta), «How to Create Fields/References» [82].

**Backstage (верифицировано).** New Frontend System — официально рекомендуемый путь (экспорты под `/alpha`; create-app генерирует NFS-приложения); app = `createApp({ features })` с автоматическим feature discovery; «It is possible to enable, disable and configure extensions individually in the `app-config.yaml`»; конфиг может лениво грузиться с бэкенда (`configLoader`); escape hatch — код с extension overrides [83]. UI-структура вносится кодом через **blueprints**: `PageBlueprint.make({routeRef, path, title, icon, loader})` (title/icon сами наполняют сайдбар), `EntityContentBlueprint` (из `plugin-catalog-react/alpha`) — декларативный вклад в страницу сущности (табы/секции = extension points); всё lazy-loaded; плагин ставится без кода (default export + feature discovery); утилитарные API — `ApiBlueprint` с возможностью замены [83]. app-config — схема, сшитая из `configSchema` всех пакетов: superset JSON Schema Draft-07 с `visibility` (frontend/backend/secret); официальная рекомендация — «Make limited use of static configuration» (статик — только per-environment опции) [84]. **Асимметрия kind/type** — ключевая улика цены: бэкенд kind-agnostic, но «Adding a kind has a very large impact… There will be many places where code checks `if (kind === 'X')`»; кастомный kind = namespaced apiVersion + изоморфный пакет (TS-тип + JSONSchema) + CatalogProcessor + обновление плагинов; «Adding a new type takes relatively little effort and carries little risk»; менять core validation — «high risk… not recommended» [85] (вербатимы верифицированы). Пробел: страницы Scaffolder custom-field-extensions и extension-blueprints отдают 404 (документация реструктурирована), Wayback не архивировал — RJSF-binding Scaffolder и специфика `EntityCardBlueprint` остались unverified belief [86].

**LeanIX (snapshot 2020-09, medium).** Self-service — только видимость и обязательность: admin настраивает, какие секции и атрибуты показываются на Fact Sheet, и вес обязательности («Set the weight of sections to '1' to treat them as mandatory, or to '0' for optional»); скрытие секции lossless («no data is removed, it is even still accessible via the API»); best practice — скрыть неиспользуемые секции при онбординге [87]. Изменения модели данных — «Configuration Add-Ons», исполняемые vendor'ом (не self-service, edition-gated): обоснование явно — «might cause data loss or legal violations if used in a wrong way»; процесс — шаблоны требований, test workspace, засеянный из боевого, «four weeks time to develop the first iteration», staged go-live [87]. Посылка — тюнить best-practice модель, не строить новую; переиспользовать существующий тип не рекомендуется, потому что «certain reports rely on the out-of-the-box dependencies» — **жёсткая привязка отчётов/экранов к конкретной метамодели** (контрпример schema-driven UI) [87].

**Формы (верифицировано).** RJSF v6.11.0: «capable of building HTML forms out of a JSON schema», авто-генерация формы из schema; презентация — отдельный слой `uiSchema` по путям свойств; с v5 обязателен валидатор (`@rjsf/validator-ajv8`); философия позиционирует schema-driven генерацию для «any data, sight unseen» — ровно кейс каталога поверх развивающейся метамодели [88].

**Синтез D7 — граница конфиг/код и паттерны для структуры экранов:**

1. Двухслойная декларативность, общая для всех читаемых референсов: слой данных (типы, поля, поля связей, порядок, группы, Priority Fields, секции) — конфигурация/данные метамодели; слой визуализаций (граф, timeline, радар, matrix) — фиксированные React-модули, параметризуемые конфигом [80][81][83][85].
2. Ardoq доводит schema-as-data до layout (field order из метамодели, zero-instance triples, Field Groups в админ-зоне метамодели); Backstage останавливается на границе kind — для v1.5 все 15 типов сущностей — данные, поэтому UI обязан рендериться из метамодели, не из кода [80][85].
3. Формы = RJSF-паттерн: JSON Schema (структура/валидация) + uiSchema (презентация) + код (кастомные виджеты) — генерация форм редактирования из схемы типа [88].
4. Контрпример LeanIX: UI-конфиг самсервис, но метамодель — vendor Add-On с 4-недельным SLA, а отчёты хардкодятся под стандартную модель — предупреждение для v1.5: ни один экран не должен зависеть от конкретного имени типа [87].
5. Расширение UI под типы — через extension points (Backstage `EntityContentBlueprint`) и admin-группы (Ardoq Field Groups), а не через ветвления в коде [83][80].
6. Дефолтные состояния обязаны работать: пустая конфигурация даёт пригодный UI (Ardoq: плоский алфавитный список, «absent groups → page unchanged») [80].
7. Static config — только per-environment опции (Backstage guidance); UI-конфигурация как данные (экран-схемы) — отдельный слой, не app-config [84][80].

## Cross-dimension insights

1. **Связь — один примитив на всех экранах.** Тройка Source→Type→Target в карточке (D1 [9]), references-as-columns в инвентаре (D6 [72]), re-root drilldown в графе (D2 [19]), join радара с приложениями (D4 [53]) — один и тот же примитив проявляется на каждом экране. Для метамодели с 20 типами связей это значит: один переиспользуемый компонент отображения связей (таблица с группировкой тройками + графовая окрестность), а не реализация на каждый экран.
2. **Даты — второй универсальный примитив.** Timeline-бары из date-range полей (D3 [38]), lifecycle-view инвентаря (D1 [3]), time-frame фильтры (D6 [79]), impact «at key milestones» (D3 [34]) — жизненный цикл и план выражаются одними и теми же данными. Экран дорожной карты — это проекция date-range/date полей над связями initiative→сущность, а не отдельная модель данных.
3. **Граница «конфиг/код» проходит по одному правилу во всех референсах:** всё, что есть в метамодели (типы, поля, связи, секции, порядок) — данные; все виды отображения (граф, timeline, радар, matrix, таблица) — фиксированный код, параметризуемый данными (D7 [80][85], D2 [18], D3 [38]). Цена нарушения подтверждена с двух сторон: Backstage — «very large impact» нового kind (D7 [85]), LeanIX — отчёты, хардкодно привязанные к стандартной метамодели (D7 [87]).
4. **Демонстрация командам — режим, а не множество экранов.** Дашборды поверх view (D1 [8]), presentation shell над живыми view с explore-mode (D3 [42]), shareable сериализованные состояния (D2 [19][24]) — все три инструмента строят «показать команде» поверх тех же view, а не отдельными экранами. Для v1.5: каждый экран должен иметь сериализуемое состояние (URL) и встраиваемый demo-режим.
5. **Два анти-паттерна с ценой, доказанной вендорами.** Traversal по загруженному датасету (Ardoq молча теряет ветки закрытых воркспейсов, D2 [22]) и хардкод экранов под конкретные типы (LeanIX, D7 [87]) — оба устраняются одним и тем же архитектурным решением: обход и рендер всегда идут от хранилища метамодели, UI ничего не знает о конкретных типах.
6. **Радар «связанный с продуктами» — линза, не экран.** Ни один референс не линкует радар к инвентарю автоматически (D4 [47][48][53]); единственный паттерн — LeanIX: радар как report поверх связей. В v1.5 это реализуется без нового типа экрана: элемент радара = сущность Технология, deep-link в отфильтрованный инвентарь по связи.

## Recommendations

Downstream-привязка: рекомендации потребляются фазой дизайна UI (декомпозиция S5 Web UI техдизайна метамодели v1.5); каждая помечена confidence-базисом.

1. **Экранная карта из семи модулей**: Инвентарь (таблица + фильтры-чипы + колонки из метамодели), Карточка сущности (табнутый профиль + guarded табы), Граф (standalone-страница + виджет-окрестность на карточке), Дорожная карта (timeline), Тех-радар, Поиск (omnibox + advanced), Дашборды/демо. Каждый модуль — фиксированный React-модуль, конфигурируемый данными метамодели. _Basis: конвергенция 4 инструментов по D1–D2; confidence high._
2. **Экран-схемы как данные**: layout карточки (секции, группы полей, Priority Fields, порядок, колонки таблицы) генерируется из метамодели v1.5; формы редактирования — RJSF-паттерн (JSON Schema из схемы типа + uiSchema презентации). Дефолт без конфигурации — работоспособный UI. _Basis: D7 [80][88], verified; confidence high._
3. **Связи**: группировка тройками с click-through на обе стороны; drilldown = re-root; matrix как editing-режим массового создания; обход по БД. _Basis: D1/D2/D6, verified; confidence high._
4. **Поиск**: PG-native без внешнего движка при ≤20k сущностей — stored generated tsvector + GIN (jsonb_to_tsvector + setweight name/description), websearch_to_tsquery, ts_rank_cd, фасеты GROUP BY; два уровня (⌘K omnibox с ID-first по business_id + declarative advanced builder ALL/ANY); permission-aware; подсветка ts_headline — опционально и с sanitize. До дизайна схемы — подтвердить `\dF` на живом PG16. _Basis: D6, verified; confidence high._
5. **Тех-радар**: модель данных Backstage (quadrants/rings/entries + timeline[{date, ringId, moved}], без coordinates), авторинг MD+frontmatter в GitLab-релизных папках (паттерн AOE), радар = сущности Технология + deep-link в инвентарь. _Basis: D4, verified; confidence high._
6. **Дорожная карта**: фазы = date-range поля, milestones = date поля (ромбы), окна-минимумы layout'ов как в Ardoq; не привязывать roadmap к scenario-веткам (ограничение Scenarios); target-state — изолированная ветка данных. _Basis: D3, verified; confidence high._
7. **Документы (ADR/HLD/RFC)**: каталог хранит ссылки (аннотации), тела — MD в GitLab; ADR — guarded таб + типизированный поисковый коллатор; статус-enum proposed/accepted/rejected/superseded с парными supersede-связями; шаблон HLD — arc42 (12 секций, Section 03 привязывает к системе); MADR 3.x пока Backstage-плагин не читает 4.x. _Basis: D5, verified; confidence high._
8. **Демо-режим**: сериализуемые состояния view (URL), embeddable-режим поверх живых данных, explore-drilldown опционален. _Basis: D3 [42], D2 [24]; confidence medium (один источник на explore-mode)._
9. **Избегать**: хардкода UI под имена типов (LeanIX), traversal по загруженному датасету (Ardoq), xyflow для org-use (лицензия), статического app-config для UI-структуры. _Basis: D7/D2/D4; confidence high._

## Open questions

1. **Русский FTS-конфиг на живом PG16.** Документация свидетельствует, что `russian` встроен, но enumerация не выполнена. Что нужно: `SELECT confname FROM pg_catalog.pg_ts_config ORDER BY 1;` (или `\dF`) на целевом инстансе до дизайна tsvector-колонок [77].
2. **Текущие экраны SAP LeanIX.** Все LeanIX-доказательства — снапшоты 2020–2021; продукт под SAP эволюционировал (docs переехали на JS-SPA help.sap.com). Что нужно: сессия с браузером или свежие PDF-гайды SAP для верификации A&R Planning и радара [7][34].
3. **Backstage Scaffolder-RJSF и EntityCardBlueprint specifics.** Страницы 404 после реструктуризации docs; влияет только на дословное копирование паттернов NFS. Что нужно: найти новые URL (sitemap backstage.io) [86].
4. **Фасетные счётчики как UX-паттерн.** Реализация известна (GROUP BY), канонического UX-источника (типа NN/g) не добыто — некритично для дизайна [73].
5. **Практические лимиты интерактивных графов.** Ни один инструмент не документирует node-count лимиты; что нужно: нагрузочное тестирование на реальном объёме (тысячи связей) для выбора SVG vs WebGL-рендера [20][30][31].
