# D5 r1 — Backstage teardown (assistant 1, round 1)

Method note: all budgets spent (15 tool calls, 8 distinct sources read), accessed 2026-10-04.

## Questions (D5 — Backstage software catalog system model teardown)

1. Core kinds: official definitions + rationale for the decomposition
2. Relation types: full list, directionality, semantics, derivation from YAML descriptors
3. Entity schema: envelope, metadata, annotations/labels/links; official extensibility story — supported vs discouraged
4. Ownership model (Group/User, ownedBy/memberOf)
5. Design philosophy: catalog as graph, YAML + processors, minimalism, locations/orphans, idempotent ingestion
6. What Backstage consciously does NOT model + recommended path for "more"

## Findings

**Q1 — kinds**
- 9 kinds documented in the descriptor format: Component, API, Resource, System, Domain, Group, User, Location, Template (Template at `apiVersion v1beta2`, all others `v1alpha1`) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Three core entities: Components ("individual pieces of software"), APIs ("the boundaries between different components"), Resources ("physical or virtual infrastructure needed to operate a component") — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/system-model/ — confidence: high — class: doc
- Rationale: "standardize on a few core entities ... allows us to build specific plugins around them"; rollout was Component-first, API/Resource later — backstage/backstage ADR005, n.d. (early-stage; Component-only), accessed 2026-10-04, https://raw.githubusercontent.com/backstage/backstage/master/docs/architecture-decisions/adr005-catalog-core-entities.md — confidence: high — class: standard
- APIs are "first class citizens" and the "primary way to discover existing functionality"; must be machine-readable (well-known spec.type: openapi, asyncapi, graphql, grpc) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/system-model/ — confidence: high — class: doc
- System = "collection of resources and components that exposes one or several public APIs"; hides private APIs/resources so owners can evolve implementation; "typically at most a handful of components" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/system-model/ — confidence: high — class: doc
- Domain = groups of systems sharing terminology/domain models/KPIs ("bounded context"); subdomain hierarchy via `spec.subdomainOf` — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/system-model/ — confidence: high — class: doc
- Location kind = "marker that references other places to look for catalog data" (spec: type/target/targets/presence required|optional) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- System-model page still carries "This description originates from this RFC. Note that some of the concepts are not yet supported in Backstage." (needs 2nd source) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/system-model/ — confidence: high — class: doc

**Q2 — relations**
- Relation anatomy: source (entity holding it) → target (entity ref) + type; directional; documented ones come in inverse pairs (A ownedBy B ↔ B ownerOf A); list explicitly "non-exhaustive" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: standard
- 7 documented pairs: ownedBy/ownerOf, providesApi/apiProvidedBy, consumesApi/apiConsumedBy, dependsOn/dependencyOf, parentOf/childOf, memberOf/hasMember, partOf/hasPart — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: standard
- Semantics: providesApi = "hosts callable endpoints"; consumesApi = "depends on endpoints of the API"; dependsOn = general "in need of that other entity for an entity to function" (build-time libs, runtime storage); partOf/hasPart = component→component, component/API/resource→system, system→domain, domain→domain — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: standard
- Relations are never authored in YAML: processors deduce them from spec fields (spec.owner→ownedBy; spec.providesApis/consumesApis; spec.dependsOn/dependencyOf; spec.parent+children; spec.memberOf; spec.system/domain/subcomponentOf/subdomainOf→partOf/hasPart); relations are read-only output with fields type/targetRef/metadata — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Component `spec.subcomponentOf` and Domain `spec.subdomainOf` generate partOf/hasPart relations — no official `subcomponentOf` relation type on the docs page (needs 2nd source) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Relations (not spec fields) are the authoritative copy: owner may come from e.g. CODEOWNERS; spec refs shortened, with default target kinds (owner→Group, system→System, providesApis→API, dependsOn→Component|Resource) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Relations may dangle (target may not exist); stitching merges incoming + outgoing relations from all processors; relations live in a dedicated relations table — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: doc

**Q3 — schema & extensibility**
- Envelope = `apiVersion` + `kind` + `metadata` + `spec`; the apiVersion+kind tuple tells a parser how to read the rest; `backstage.io/` prefix reserved; orgs add kinds under their own apiVersion space (e.g. `my-company.net/v1`) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- metadata: name (required, ≤63 chars, `[a-z0-9A-Z]` separated by `[-_.]`, unique per kind+namespace, case-insensitive), namespace (optional, default `default`), uid (output-only, unstable — use string entity refs), title, description, labels (k8s-style, classification/filtering), annotations (k8s-style, external-system references, string values only), tags ("no special semantics"), links (url/title/icon/type; "the semantics of the type field are undefined") — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Unknown fields under metadata and spec are stored verbatim but officially discouraged (future-core collision risk; "lives more comfortably" in labels/annotations or a new type) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- Custom annotations/labels: supported, "no risk or impact to other systems" if naming rules followed; `backstage.io/` reserved; domain-prefix convention (e.g. `pagerduty.com/`); unprefixed keys instance-local — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- Custom kinds: supported — catalog backend kind-agnostic at storage/API level, but "adding a kind has a very large impact" (plugins hardcode `if (kind === 'X')`); documented pattern: TS type + JSONSchema + custom processor with validateEntityKind + postProcessEntity emitting relations — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- Replacing validation rules (field validators, replacing `BuiltinKindsEntityProcessor`) is high-risk, "not recommended in normal cases"; new apiVersion of an existing kind ≈ forking the kind, no plugin-parse guarantees — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- Custom relation types: officially free — any processor can emit them; must stay directed source→target entity refs; "we do not have any namespacing/prefixing scheme for relation types"; adopters advised to prefix (`myCompany-maintainerOf`/`myCompany-maintainedBy`); reusing well-known relation types for new purposes = "uncharted territory" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- status root field is read-only `items[]` (type/level/message/error); custom status item types = "simple, low risk"; new fields under status = undefined semantics; mechanics to emit custom statuses "not in place yet" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: doc
- Per-environment entities (mytool-dev vs mytool-prod) officially discouraged: keep one canonical Component; plugins show all deployed environments in one view; split only for coexisting major API versions, "use sparingly" (needs 2nd source) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice

**Q4 — ownership**
- Owner = "the singular entity (commonly a team) that bears ultimate responsibility ... authority and capability to develop and maintain it"; others may touch the entity but one ultimate owner — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: doc
- ownedBy is "for display purposes ... not to be used by automated processes to for example assign authorization in runtime systems" (repeated for Component, API, Resource, System, Domain, Template) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: doc
- `spec.owner` required on Component/API/Resource/System/Domain, optional on Template; default target kind Group; generates ownedBy + inverse ownerOf — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard
- Groups: `spec.parent` (max one parent; multi-root hierarchies supported) + required `spec.children` → parentOf/childOf; Group `spec.members` / User `spec.memberOf` → hasMember/memberOf; memberships listed are direct only ("no transitive memberships") (needs 2nd source) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard

**Q5 — design philosophy**
- Catalog = "a hub of sorts": entities ingested from authoritative sources, held in a DB, subject to continuous automated processing, served via API; most common source = YAML files in VCS next to the code, "maintained by the respective owners"; catalog "makes sure to keep itself up to date" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/life-of-an-entity/ — confidence: high — class: doc
- Pipeline: ingestion (entity providers with per-provider buckets; eager deletion on provider removal) → processing (policies + processors, per-entity, distributed; processors emit entities/relations/errors; processing never deletes) → stitching (fixed, non-modifiable assembly of processed entity + all relations + errors into the API-visible entity; changes to stitching must happen in ingestion/processing instead) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/life-of-an-entity/ — confidence: high — class: doc
- Format lineage: YAML multi-doc files (recommended name `catalog-info.yaml`); "draws heavy inspiration from the kubernetes object format"; carries over "user experience, learnings, and certain pieces of metadata" from Spotify's homegrown internal catalog; registration methods deliberately open (manual, CI/CD push, webhooks) — backstage/backstage ADR002, n.d., accessed 2026-10-04, https://raw.githubusercontent.com/backstage/backstage/master/docs/architecture-decisions/adr002-default-catalog-file-format.md — confidence: high — class: standard
- Orphaning: internal graph edges (parent→emitted child, explicitly "not the same thing as relations") re-evaluated each processing pass; severed edges with no other parent → `backstage.io/orphan: 'true'` annotation; default `orphanStrategy: delete` auto-removes orphans, `keep` optional; explicitly deleting a parented entity just reappears (needs 2nd source for the default) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/life-of-an-entity/ — confidence: high — class: doc
- API entities "typically indexed from existing definitions in source control" and Resources "typically indexed from declarative definitions (e.g. Terraform, GCP Config Connector) and/or inventories from cloud providers" — catalog mirrors existing sources of truth rather than duplicating them (needs 2nd source) — backstage/backstage ADR005, n.d., accessed 2026-10-04, https://raw.githubusercontent.com/backstage/backstage/master/docs/architecture-decisions/adr005-catalog-core-entities.md — confidence: high — class: standard
- Minimalism is structural: few core kinds (ADR005), spec.type/lifecycle values "accepted any" with taxonomy left to the adopter, System/Domain explicitly "optional" concepts — Backstage docs (next) + ADR005, n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: high — class: standard

**Q6 — boundaries**
- Owner relation explicitly not an authz mechanism (runtime authorization out of scope) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/well-known-relations/ — confidence: high — class: doc
- No environment/deployment entities: one canonical entity per piece of software; deployed versions/environments surfaced by plugins inside the entity view — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/extending-the-model/ — confidence: high — class: practice
- Retrieved docs contain no runtime-state/health modeling in the core model; Resource carries only type/owner/system/dependsOn (absence-based, low strength) — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/descriptor-format/ — confidence: medium — class: doc
- Recommended path for "more": integrate external systems via entity providers (scheduled/webhook sync), processors (enrich/annotate/emit children), incremental entity providers (large paginated sources) "rather than duplicating everything in YAML files" — Backstage docs (next), n.d., accessed 2026-10-04, https://backstage.io/docs/next/features/software-catalog/external-integrations/ — confidence: high — class: doc
