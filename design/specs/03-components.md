# 03 — Компоненты проекта

Проект it-landscape-v2 использует кит heroui. Экспериментальный UI можно писать прямо в экране или локальном файле: отдельная папка, реестр, stories и версия не нужны. `python3 .canvas/board.py components` обнаруживает локальные экспорты автоматически; уже записанные разделы должны соответствовать существующему коду.

Панель «Компоненты» разделена на «В этом проекте» и «Подключённые библиотеки». Общих библиотек может быть несколько — по брендам или продуктам. Сначала агент ищет готовое среди локальных и подключённых компонентов, сверяет возможности кита; затем предлагает композицию или кастом. Дизайнеру не нужно заранее выбирать техническую категорию.

## Сохранение из макета

«Сохранить компонент проекта» — короткий диалог: границы, название, понятные настройки («Заголовок», «Картинка», «Показывать цену», «Компактный вид»), preview того, что будет выделено. Агент сохраняет внешний вид и поведение экрана. Экземпляры связаны с компонентом; текст, цвет, картинки и предусмотренные настройки меняются в месте использования, не переписывают исходник и не меняют другие экземпляры. Локальный компонент можно свободно развивать в проекте.

## Публикация

Только «Опубликовать в общую библиотеку» (`canvas-component promote`) начинает отдельную подготовку. Выбираются библиотека и состав пакета; агент проверяет длинный текст, отсутствие картинки, узкий экран, состояния, доступность, API, стили, ассеты и вложенные зависимости. Подготовку можно приостановить и продолжить проектировать экраны. Принятие экрана и старт новой задачи её не запускают.

Статусы: `local` — компонент проекта; `candidate` — готовится к публикации; `shared` — связан с опубликованной версией. Уровни `концепт / принят / доработан` и старые версии сохраняются. Готовность библиотеки проверяется отдельно от сценариев макета: `package` не требует полного API и матрицы состояний от локальной реализации.

Общие библиотеки подключаются явно (`library connect`), готовый пакет публикуется через Git (`library publish --library <id>`). Публикация требует принятого результата, необходимых примеров, документации и тестов. Types/styles/constants разделяются по сложности, фиксированного шаблона из девяти файлов нет. Версия — semver от 1.0.0, история — CHANGELOG.md; версию и историю согласованно обновляет `component version`. Major меняет публичный API и требует явного согласования владельца.

После публикации общая библиотека — единственный источник. Проект хранит связанную материализацию принятой версии и отпечаток исходников в `library.lock.json`. Обновление только явное. Для другой структуры — «Создать локальную версию» (`library fork --name <Имя>`): новый компонент проекта с происхождением, оригинал сохраняется, автоматического слияния нет.

## Запись сохранённого компонента

```markdown
## ИмяКомпонента

**Файл:** `src/components/product-card.tsx`
**Статус:** `local`
**Способ:** `composition`
**Из кита:** Card, Button
**Где используется:** catalog
```

Для кандидата добавляются границы, API, состояния, ссылки на примеры, уровень, приёмка и версия. Локальному наброску они не обязательны. Повторное использование не переводит компонент в кандидаты автоматически. Совпадение имени с компонентом кита требует пояснения «одноимённый компоненту кита намеренно»; обычно лучше назвать композицию по задаче.

## Нативное, не своё

Часть интерфейса даёт платформа, и рисовать её в JS запрещено — на устройстве своя копия хуже штатной (нет автозаполнения, словаря, жестов, доступности и привычки пользователя), а сторож реестра (`board.py components`) ловит самые частые подделки. Нативными обязаны быть:

| Что | Как | Почему |
|---|---|---|
| клавиатура (в том числе цифровая, для кода из SMS/бота) | `TextInput` с `inputMode`/`keyboardType`, `InputOTP` кита с нативным вводом | своя клавиатура ломает автозаполнение кода, раскладку, диктовку и работу в перчатках |
| выбор даты и времени | `@react-native-community/datetimepicker`, expo | системный пикер знает локаль и календарь |
| камера и сканер штрих-кодов | `expo-camera`, аппаратный сканер ТСД | JS-сканер медленнее и ест батарею |
| системные диалоги: разрешения, выход из приложения, шаринг, выбор файла | `expo-*` API, `Share`, `Linking`, `DocumentPicker` | пользователь узнаёт системный диалог и доверяет ему |
| жест «назад», статус-бар, safe area, вибрация | навигация Expo Router, `expo-status-bar`, `react-native-safe-area-context`, `expo-haptics` | это контракт платформы, а не дизайна |
| тосты и снекбары | `Toast` кита (единый стиль приложения) — **не** `ToastAndroid` | исключение из правила: уведомление внутри приложения — часть его дизайна |

Не нативными, а из кита остаются: кнопки, поля, чипы, вкладки, шторки, диалоги приложения, списки, карточки — то, что рисует дизайн продукта.

## Профиль кита

Кит проекта (heroui) описан данными — профилем кита в канвасе (`.canvas/kits/<кит>/profile.json`, формат — `.canvas/docs/CANVAS.md` §6.4): что кит отвечает на типовую задачу (диалог подтверждения, загрузка, строка списка, статус, поле формы…) и с какого образца начать — это печатает `board.py brief`; шкала шрифта, шаг отступов, что считать главной кнопкой и словарь исправлений — этим меряет и советует линтер экранов; правила разметки кита — сторож исходников в `board.py check`. Своё проект задаёт в конфиге дизайн-пакета (`design/canvas.config.json` → `kit`, пути — от `design/`):

- `"samples": {"confirm": {"file": "app/src/screens/Orders.tsx", "symbol": "CancelOrderDialog"}}` — образцы проекта по ролям задачи (`.canvas/kits/_roles.json`): после первого принятого экрана лучший образец — ваш код, и `brief` называет его вместо образца демо канваса;
- `"patterns": "specs/patterns.local.md"` — своя галерея образцов: раздел `## <запись>` с названием роли («Подтверждение действия») или записи галереи кита;
- `"profile": "<система>.profile.json"` — свой профиль для закрытой дизайн-системы компании (тот же формат; `extends` — профиль кита канваса, на котором она построена): тогда подсказки, шкала, словарь исправлений, правила сторожа и MCP — из него.

## Отступления от кита

Что кит решил не по норме, а проект принял осознанно: часть компонента меньше 24 dp (например, кнопка очистки поиска, `SearchField.ClearButton` 20 dp — WCAG 2.5.8 допускает её при 24 dp свободного места вокруг), контраст текста кита ниже AA при 3:1 и выше. Сюда пишет агент по строкам линтера экранов `так решил кит`; каждая запись — компонент, где, почему принято и что скажет владелец. Заголовки подразделов здесь — русские: сторож реестра разбирает только разделы с именем компонента латиницей.

## Линтер экранов: что он ловит

`python3 .canvas/board.py uilint` (в `gatesFull`; по умолчанию все профили и обе темы, точечно `--only <id>`, `--profile <id>`, `--theme dark`, отчёт `--json build/uilint.json`) проверяет снятые экраны по дереву блоков и пикселям кадра — то, чего не видно в коде:

- доступность: контраст текста ниже AA (4,5:1; крупному хватает 3:1), цели нажатия ниже 24 dp (P1, нижняя граница WCAG 2.2; ссылка в строке текста целью не считается) и ниже 32 dp на сенсорном экране — телефон и планшет (P2; ориентир платформ — 44 dp), нажимаемые элементы без имени, наезд двух целей;
- раскладка: блок за правым краем окна, обрезанный текст;
- кит: две главные кнопки на экране (что считать главной — профиль кита: у HeroUI `variant="primary"`), переключатель без части, которая рисует выбор, чипы статуса разного смысла одного вида, модификаторы кита, которых нет в реестре семантики;
- тема и типографика: сплошные цвета мимо ролей темы, размеры шрифта вне шкалы кита, отступы своих блоков вне шага шкалы.

Каждая строка говорит, что взять вместо. P1 и P2 чинятся в коде, экран переснимается — владельцу кадр уходит уже без них; P3 — косметика и решения самого кита («так решил кит»): чинить не обязательно, но назовите их в отчёте владельцу. Что нельзя измерить (пёстрый фон, блок под панелью или вне кадра), линтер называет «не измерено», а не выдумывает.

Рядом `board.py shotdiff` — на сколько процентов каждый кадр разошёлся с прошлой версией в git (карты — `design/build/canvas-shotdiff/`): после правки одного экрана меняться должен только он.

**Свойства экземпляра (решение владельца 2026-10-02).** Текст, цвет, размер и другие параметры на макете меняются в месте использования через публичные props/варианты. Это не правка исходника, дефолтов или версии библиотеки. Если нужного параметра нет, предложи отдельную доработку API или локальную композицию; не переписывай общий компонент автоматически. Переключатели preview временные и не сохраняют изменения в библиотеку.
